## 一、整体架构

```
【离线：建库】
岗位表 8,836 条 ──┐
                  ├─→ 卡片生成（岗位卡 8,836 + 结论卡 16）
任务4~7 的关键结论 ─┘        │
                            ↓
                 BGE-small-zh-v1.5 向量化（512 维，L2 归一化）
                            ↓
                 FAISS IndexFlatIP（余弦检索） + 卡片元数据 JSON

【在线：问答】
用户问题 ──→ DeepSeek（function calling）──决定调哪个工具──→ 本地工具执行
                ↑                                              │
                └──────────── 工具结果回灌（含来源）←───────────┘
                            ↓
                 带来源与局限声明的中文回答（最多 6 轮工具调用）
```

**关键设计：不让大模型"凭记忆答题"，答案里的每个数字都来自本地工具**（检索结果 / 结构化统计 / 匹配模型）。

## 二、知识库（RAG）

### 2.1 卡片构成

| 卡片类型 | 数量 | 内容 | 作用 |
|---|---|---|---|
| **岗位卡** | 8,836 | `岗位：…。公司：…。城市：…。薪资：…（下限-上限）。经验要求：…。学历要求：…。技能标签：…。职位描述摘要：…（前 160 字）` | 回答「有哪些岗位」「某城市某方向的工作」 |
| **结论卡** | 16 | 任务4/5/6/7 的关键结论，**每张标注来源**（对应报告/图号）：薪资分位与经验-薪资曲线、经验结构、学历门槛、技能热度、企业集中度、回复活跃度、地域分布、匹配权重与性能、评分模型指标、聚类画像（含二阶细分）、多模型对比、数据质量 | 回答「薪资中位数多少」「岗位分几类」这类统计型问题 |

- 卡片明细可审计：`data/processed/RAG_知识卡.csv`（含 id/类型/文本/元数据）。
- 元数据（`data/rag/jobs_kb_cards.json`）：类型、岗位ID、岗位名称、城市、薪资、公司、来源 → 支持**溯源**。

### 2.2 Embedding 与向量库的选择（含两次踩坑，如实记录）

| 选择 | 理由 |
|---|---|
| **本地 BGE-small-zh-v1.5** | ① **DeepSeek 官方不提供 embedding 接口**，必须另找嵌入模型；② 中文效果好、模型约 95MB、512 维，CPU 可跑；③ 岗位数据不出本机。经 `HF_ENDPOINT=https://hf-mirror.com` 下载 |
| **FAISS** | ① 课程列出的候选向量库之一（Chroma/FAISS/Milvus）；② `IndexFlatIP` + 归一化向量即**精确余弦检索**，无需训练索引 |
| ❌ 最初用 Chroma 1.5.9 | 本地持久化写入成功，但**跨进程重新加载时报 `Error loading hnsw index`**，无法用于"建库进程/问答进程分离"的场景，故弃用 |
| ⚠️ FAISS 索引不落盘 | **FAISS 的 C++ 层在 Windows 上无法打开中文路径**（本项目目录含中文），`faiss.write_index` 直接失败。最终方案：向量用 `.npy` 落盘（numpy 支持中文路径），**索引在检索端加载时内存重建**（8,852 × 512 重建 <0.1s，代价可忽略） |

**向量化耗时**：8,852 张卡片在 CPU 上约 163 秒（约 54 条/秒），向量已缓存为 `data/rag/embeddings_8852_512.npy`，重建知识库时秒级完成。

## 三、检索召回评估（课程硬要求）

**评估设计**：30 条真实问题 × 3 种检索模式，**可自动判定**——
① 岗位检索类（10 条）：真值 = 在清洗后岗位表上按「城市 + 关键词」算出的岗位集合；
② 结论类（20 条）：真值 = 应命中的结论卡（校验其「来源」字段）。

| 模式 | 说明 | P@5 | R@5 | 溯源正确率 |
|---|---|---|---|---|
| 纯语义（全库） | 8,852 张卡放同一索引 | **0.147** | 0.045 | 0.147 |
| **分类型路由** | 统计型问句查结论卡、其余查岗位卡 | **0.340** | 0.114 | 0.340 |
| **路由 + 城市元数据过滤** | 岗位检索类额外按城市硬过滤 | **0.353** | 0.147 | 0.353 |

**三条结论**：
1. **结论卡会被岗位卡淹没**：16 张 vs 8,836 张，纯语义检索几乎召不到结论卡（P@5 仅 0.147）。加入"分类型路由"后整体 P@5 提升到 0.340（**+131%**），结论类问题的溯源正确率接近 1.000 —— 这是本任务最有价值的一条工程经验。
2. **城市这类硬条件必须靠元数据过滤**：向量只表达语义，「厦门」在语义空间里的权重压不过「Java」；岗位检索类加城市过滤后 P@5 从 0.283 升到 0.307。
3. **R@5 偏低是正常的**：真值集合常有几十上百个岗位，而 Top-5 最多命中 5 个；评估应以 P@5 与溯源正确率为主。

> 逐题结果（含每题 Top1 与判定说明）见 `data/processed/RAG召回评估.csv`，汇总见 `RAG召回评估.md`。

## 四、Agent 智能体（Function Calling + 工具编排）

### 4.1 工具清单（9 个）

| 工具 | 参数 | 返回 | 底层实现 |
|---|---|---|---|
| `search_kb` | query, k | **结论卡**原文 + **来源（报告/图号）** | 知识库「结论卡」专用检索（v4 新增，见 4.4） |
| `search_jobs` | query, k, city | 语义检索到的岗位（含相似度） | FAISS + BGE（知识库） |
| `filter_jobs` | city, keyword, salary_min, edu, k | **命中总数** + 样例 | 结构化规则筛选（8,836 条 CSV） |
| `salary_stats` | city | 样本数、下限/上限中位数、区间中点中位数、P25/P75 | 薪资数值列统计 |
| `salary_rank` | top | **各城市薪资排名** | 按城市聚合（v3 新增，用于替代逐城查询） |
| `city_list` | — | 覆盖城市与各城市岗位数 | 岗位表聚合（v3 新增） |
| `match_resume` | resume_text, top_n | Top-N 岗位 + 6 维得分 + 推荐理由 | **任务6 匹配引擎**（含简历解析） |
| `cluster_profile` | name | 聚类画像（规模/薪资中位数/主要岗位与技能） | **任务7 聚类结果** |
| `kb_stats` | — | 卡片构成、Embedding 模型、召回指标 | 知识库自述 |

### 4.2 编排流程与工程约束

```
问题 → LLM 选工具 → 本地执行 → 结果（≤6000 字符）回灌 → LLM 汇总（带来源）→ 回答
```
- **最多 6 轮**工具调用、**最多 12 次**工具执行；超限则带着已有信息作答（不空转）。
- **缓存**：`data/rag/agent_cache.json`，键 = `Prompt版本 + 模型 + 问题`；演示时相同问题秒回且结果可复现（改 Prompt 版本会自动失效）。
- **超时与重试**：单次请求 90s，失败重试 2 次（指数退避）。
- **失败如实返回**：工具异常返回 `ok=false` + 错误信息，Prompt 明确要求"直说没查到，不要用常识补全"。
- **调用日志**：`data/rag/agent_calls.jsonl`（每次问答的工具调用、tokens、耗时），可用于成本核算与复盘。

### 4.3 工作流编排实测（30 问，`data/processed/RAG_工作流编排统计.csv`）

把 RAG 召回评估的同一批 30 条真实问题交给 Agent（`python src/rag/make_triples.py`），统计它**自己串出来的工具调用序列**：

| 编排形态 | 问题数 | 占比 | 典型序列 |
|---|---|---|---|
| 2 次工具调用 | 21 | 70% | `search_kb → search_kb`（5）、`city_list → search_jobs`（3）、`search_kb → cluster_profile`（3）、`search_kb → filter_jobs`（3） |
| 1 次工具调用 | 8 | 27% | `cluster_profile`（2）、`search_jobs`、`salary_stats`、`salary_rank`、`city_list` |
| 3 次工具调用 | 1 | 3% | `search_jobs → city_list → filter_jobs` |
| 未调用工具 | 1 | 3% | 第 23 问（岗位表无对应字段 → 如实回答「查不到」） |

- **工具使用频次**（30 问共 53 次调用）：`search_kb` **19** ｜ `city_list` 9 ｜ `search_jobs` 8 ｜ `filter_jobs` 7 ｜ `cluster_profile` 5 ｜ `kb_stats` 2 ｜ `salary_stats` 2 ｜ `salary_rank` 1。
- **编排规律**：绝大多数问题由 **LLM 自主两步完成**，且呈「**先取口径（`search_kb`）、再取数据（`search_jobs`/`filter_jobs`/`cluster_profile`）**」的模式——即 Agent 先确认「本系统这个指标是怎么算的」，再拿数据回答，而不是先猜口径再凑数字。
- 该序列**不是代码里写死的流程**，而是 Prompt 规则 + 工具描述引导下 LLM 每次现场决策的结果；`RAG_工作流编排统计.csv` 就是把这种"隐式工作流"落成可审计证据。

### 4.4 `search_kb`：为什么单独开一个「结论卡检索」工具（v4 的核心改动）

背景：任务4~7 的关键结论（薪资中位数口径、匹配权重、评分模型指标、聚类画像、多模型对比）被整理成 **16 张结论卡**入库，但 30 问召回评估显示——**纯语义检索时结论卡会被 8,836 张岗位卡淹没，P@5 只有 0.147**。

后果：v2/v3 的 Prompt 虽然反复要求「不许用行业常识代替本系统数据」，但 Agent **找不到**那些数据，只能编。核对 `data/rag/agent_calls.jsonl` 里 v3 的 30 问记录，**有 3 条完全不调用任何工具**：第 12 问「薪资是用中位数还是平均数描述更合适？」、第 23 问「哪些公司回复求职者比较积极？」、第 29 问「匹配系统给一份简历打分要多久？」——直接用行业常识作答。

v4 的做法：
1. 新增 `search_kb(query, k)`，**只检索结论卡**、默认关闭「岗位卡兜底」（避免再次被淹没）；
2. Prompt 规则 2 强化为「涉及本系统统计口径/指标/模型结论的问题，**必须先查 `search_kb`**」。

效果：第 12、29 问变为**先查结论卡再作答**，答案开始引用「中位数 7,671 元 vs 平均数 8,392 元」「全量 8,836 岗打分 0.17 秒」等本系统数据；30 问**完全不用工具的问题数 3 → 1、有来源标注率 90% → 97%**；`search_kb` 成为最常用工具（19/53 次调用，占 35.8%）。

> 唯一保留的「不用工具」是第 23 问——岗位表没有回复率/响应时长字段，**没有工具可用**，Agent 如实回答查不到并给出替代问法。这正是 Prompt 想要的行为，不是待修的缺陷。

### 5.2 「问题—答案—来源」三元组（30 条，课程要求的交付物）

除 7 条演示问答外，把**召回评估用的同一批 30 条真实问题**完整跑一遍 Agent，落成三元组 `data/processed/RAG_问答三元组.csv`：

| 列 | 说明 |
|---|---|
| `问题` / `答案` | 原始提问 + Agent 的完整中文回答 |
| `来源` | **溯源字段**：回答引用的报告与章节/图号（如「人岗匹配文档 第六节/第七节」），由 `search_kb` 返回 |
| `命中岗位ID样本` / `命中岗位名称样本` | 检索命中卡片的岗位 ID 与名称（岗位类问题可回溯到具体一行数据） |
| `调用工具` / `工具调用次数` / `轮数` / `耗时秒` | 该次问答的工作流轨迹（汇总见 `RAG_工作流编排统计.csv`） |
| `prompt_tokens` / `completion_tokens` / `prompt版本` / `缓存命中` | 成本核算与版本可追溯 |

**汇总结果：30 问中有来源标注 29 条（97%）**，唯一没有来源的第 23 问（「哪些公司回复求职者比较积极？」）是因为岗位表根本没有回复行为字段，Agent 正确选择了**不编造、直接说明查不到并给出替代问法**。

## 七、成本与性能

| 项 | 实测 |
|---|---|
| 单次问答耗时 | 3.4 – 10.1s（含 1–4 次工具调用；本地工具本身 <0.5s，其余是大模型往返） |
| 30 问批量评估 | 平均 **4.2s/问**、合计 125s，平均 **1.77 次**工具调用 |
| 单次问答 tokens | prompt 3,500–4,700 ｜ completion 400–1,200 |
| 缓存命中 | 相同问题（同 Prompt 版本）**秒回、零 token** |
| 本地依赖 | `torch 2.5.1 + transformers 4.47.1`（Embedding）、`faiss-cpu`（向量检索）、`chromadb`（已装但未采用） |

> 成本控制手段：`deepseek-flash` 低价模型 + 结果缓存 + 工具调用上限 + 工具返回截断（≤6000 字符）。

## 八、局限与如实说明

| # | 局限 | 说明 |
|---|---|---|
| 1 | **无人工金标** | 检索评估的真值是规则算的，回答质量靠 7 条示例人工抽检；**不能宣称"回答准确率 X%"** |
| 2 | **结论卡只有 16 张且为人工整理** | 覆盖的报告结论有限，未覆盖的问题会落到岗位卡检索上，效果下降 |
| 3 | **岗位卡描述截断到 160 字** | 长尾细节会丢；追问细节时需回查原始 CSV（当前 Agent 未实现该工具） |
| 4 | **无公司维度检索** | 数据里没有公司 ID/规模字段（只有公司名称），无法按公司筛选（示例 7 已如实说明） |
| 5 | **只覆盖 16 城** | 北京/上海等城市查不到，Agent 会明确说明这是覆盖范围问题 |
| 6 | **向量库为内存索引** | FAISS 无法写中文路径，索引每次启动重建（8,852 条 <0.1s，当前规模无影响，数据量增大后需换方案） |
