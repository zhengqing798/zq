# Prompt 版本记录 —— 任务10 Agent 智能体

> 课程 M2 验收要求「Prompt 有版本记录」。本文件记录每一版 Prompt 的改动内容、原因与**实测效果**。
> 当前生效版本写在 `src/agent/prompts.py` 的 `PROMPT_VERSION`；Agent 的缓存键包含版本号，改版后旧缓存自动失效。

| 版本 | 日期 | 状态 | 改动内容 | 改动原因 | 实测效果 |
|---|---|---|---|---|---|
| **v1** | 2026-09-14 | 设计稿（未落地） | 起草：角色设定 + 6 个工具说明 + 「只依据工具数据回答、标注来源、不确定就直说」 | 需要一个"不编数字"的数据问答助手 | 仅评审用，未实际调用 |
| **v2** | 2026-09-14 | 已被 v3 取代 | 在 v1 基础上补齐 7 条硬性要求：① 来源标注格式；② `ok=false` 时必须直说没查到；③ 推荐要给依据；④ 主动声明已知数据局限（16 城/24.69% 经验错位/无人工金标）；⑤ 中文分点、先结论后依据；⑥ 不输出 JSON 细节；⑦ 声明能力边界 | v1 在"诚实性"上约束不够——大模型容易用行业常识补全查不到的数据 | 7 条约束生效：示例问答中数字均带来源、能力边界问题如实回答"未覆盖" |
| **v3** | 2026-09-14 | 已被 v4 取代 | ① 工具从 6 个增到 8 个：新增 **`salary_rank`**（各城市薪资排名）与 **`city_list`**（覆盖城市清单）；② 新增规则 4：「同一个问题最多调用同一个工具 2 次；需要逐项对比时优先用聚合工具」 | v2 实测暴露问题：问「薪资最高的城市是哪个」时，模型**逐城调用 `salary_stats` 12 次**并撞上工具上限（12 次），prompt tokens 高达 9,330，回答质量还不稳定 | 同一问题（示例 3）：工具调用 **12 次 → 2 次**、prompt tokens **9,330 → 4,182**、耗时 7.1s → 3.8s；「北京有没有岗位」改为先调 `city_list` 再如实回答未覆盖 |
| **v4** | 2026-09-14 | 已被 v5 取代 | ① 工具从 8 个增到 **9 个**：新增 **`search_kb`**（只检索 16 张**结论卡**、默认关闭岗位卡兜底）；② 规则 2 强化为「**先查再答**：涉及本系统统计口径/指标/模型结论的问题，必须先调用 `search_kb`，严禁用行业常识代替本系统数据」 | **在 30 问 RAG 检索评估里发现**：纯向量检索的结论卡会被 8,836 张岗位卡淹没（P@5 仅 0.147），Agent 因此**查不到本系统自己写过的结论**——核对 v3 调用日志，30 问中有 **3 条完全不调工具**（第 12、23、29 问；其中第 12、29 问正是问本系统口径），转而用行业常识作答。这正是 Prompt v2/v3 最想禁止的行为，却缺少**可达的工具** | 30 问三元组重建：**有来源标注 27/30（90%）→ 29/30（97%）**；**完全不用工具的问题 3 → 1**（仅剩无数据可查的第 23 问）；`search_kb` 成为**最常用工具**（53 次调用中占 19 次，35.8%）；第 12、29 问的答案开始引用「中位数 7,671 元 vs 平均数 8,392 元」「全量 8,836 岗打分 0.17 秒」等本系统数据 |
| **v5（当前）** | 2026-09-15 | ✅ 生效 | ① 新增规则 5「**问数量必须用 `filter_jobs`**，不要用 `search_jobs` 回答数量——它只返回 Top-k 样例，不代表总数」；② 新增规则 6「`filter_jobs` 的 keyword **只传核心专业词**（`Java`、`软件测试`），不要传『Java 开发工程师』这类组合短语」；③ 新增规则 7「返回多口径时**先报严格口径、再报宽口径**」；④ 重写两个工具的描述（`filter_jobs` 说明核心词匹配与三口径；`search_jobs` 明确标注「答不了数量」）；⑤ 顺手删掉工具清单里重复的 3 行 | **用户实测发现的真 bug**：问「福州市的 Java 岗位有多少」时，Agent 用 `search_jobs` 传了组合短语「Java 开发工程师」，只召回 **7 条**；而库里福州含 Java 的岗位实际有 **84 个（岗位名称）/ 139 个（名称或技能标签）**。根因有两层：① **工具的关键词匹配写死为「整串子串匹配」**（`keyword not in blob`），于是「Java工程师」「java」「全栈（技能含 Java）」统统搜不到；② "问数量"没有被引导到**返回总数**的工具上 | ① **匹配层修复**（`src/rag/query.py`）：归一化 → 中英混排切开 → 剥掉泛词（开发/工程师/高级…）→ 按核心词匹配，ASCII 核心词加**词边界**（`java` 不再命中 `javascript`）；② **数量口径修复**：主口径改为「名称或技能标签命中」，同时给出名称口径与含描述提及的宽口径；③ 复测：`Java` / `Java开发` / `Java 开发工程师` / `java` / `JAVA` **五种写法结果完全一致**（福州 84 / 139 / 228），8 个用例与独立真值**逐一对齐**；④ 同一问题重跑：**7 条 → 139 个**，Agent 自动改传核心词 `Java` 并调用 `filter_jobs` |

> **⚠️ 一条更正（2026-09-15，v5 重跑后发现）**：v4 时第 23 问「哪些公司回复求职者比较积极？」没有任何来源标注，当时判断为"岗位表没有该字段、不用工具是正确行为"。**这个判断是错的**：
> 知识库里**确实有一张结论卡**记录了回复积极性（来源：可视化分析报告 **图10**——`回复时效` 99.83% 为空，改用 `今日回复数`（非空 52.3%）作代理指标，360 家 ≥5 岗公司中最高分是**厦门睿云联 84.7 分**）。
> 也就是说 v3/v4 时 Agent 的"查不到"其实是**漏答**。v5 重跑后该问会先调 `search_kb`，把这条结论卡查出来，并如实说明四个局限（只记录了榜首、口径是代理指标、样本经筛选、无公司维度检索）。**这正是"先查再答"被真正落实的效果。**

## 二、v4 的实测对照（30 问「问题—答案—来源」三元组评估）

评估方式：把 `src/rag/evaluate_recall.py` 的同一批 30 条真实问题丢给 Agent（`python src/rag/make_triples.py`），逐条记录「调用工具序列 / 答案 / 来源」，产出 `data/processed/RAG_问答三元组.csv` 与 `RAG_工作流编排统计.csv`。

| 指标 | v3（8 工具） | v4（9 工具） |
|---|---|---|
| 有来源标注的问题数 | 27/30（90%） | **29/30（97%）** |
| **完全不调用工具的问题数** | **3**（第 12、23、29 问） | **1**（仅第 23 问） |
| 平均工具调用次数 | 1.70（合计 51 次） | 1.77（合计 53 次） |
| 平均单问耗时 | 4.5s | **4.2s**（30 问合计 125s） |
| 结论卡检索工具 | 无（只能落到岗位卡） | `search_kb`，**53 次调用中占 19 次（35.8%）** |

> v3 那 3 条「不用工具」的问题分别是：**12**「薪资是用中位数还是平均数描述更合适？」、**23**「哪些公司回复求职者比较积极？」、**29**「匹配系统给一份简历打分要多久？」。前两条（12、29）问的是**本系统口径**，当时 Agent 没有能查到口径的工具，只能拿行业常识答；v4 补齐为「先查结论卡」。第 23 问属于**数据里根本没有该字段**，v4 仍不用工具是**正确行为**。

**v4 工作流编排形态**（来自 `RAG_工作流编排统计.csv`，30 问）：

| 编排形态 | 问题数 | 典型序列 |
|---|---|---|
| 2 次工具调用 | 21/30（70%） | `search_kb → search_kb`（5）、`city_list → search_jobs`（3）、`search_kb → cluster_profile`（3）、`search_kb → filter_jobs`（3） |
| 1 次工具调用 | 8/30 | `cluster_profile`（2）、`search_jobs`、`salary_stats`、`salary_rank`、`city_list` 等 |

| 未调用工具 | 1/30 | 第 23 问（无对应字段，如实回答查不到） |

> 结论：**绝大多数问题在 2 次工具调用内解决**，且序列呈明显的「先取口径（`search_kb`）、再取数据（`search_jobs`/`filter_jobs`/`cluster_profile`）」模式——即 Agent 会**先确认"本系统怎么算的"，再用数据回答**。

## 三、v5 的实测对照（一次真实提问暴露的检索 bug）

### 3.1 触发与复现

用户实测提问：**「福州市有哪些 Java 岗位，列出来 top10」**。Agent 调用了 `search_jobs({"query": "Java 开发工程师", "city": "福州", "k": 10})`，**只召回 7 条**，并回答"福州按 Java 开发语义检索只召回 7 条"。

而岗位表的真值（带 ASCII 词边界统计）是：

| 口径 | 数量 |
|---|---|
| 福州岗位总数 | 1,173 |
| 岗位名称含 `java` | **84** |
| 名称或技能标签含 `java` | **139** |
| 名称/技能标签/职位描述任一含 `java` | **228** |
| 旧逻辑：`keyword="java开发"` 整串子串匹配 | 71（漏掉「Java工程师」「java」「全栈+Java技能」等） |
| 旧逻辑：`keyword="java 开发工程师"` 整串子串匹配 | **0**（库里不存在这个完整字符串） |

### 3.2 根因（两层）

1. **匹配方式写死了**：`structured_filter` 里是 `keyword.lower() not in blob` —— **整串子串匹配**。
   Agent 的"自由"只体现在**选哪个工具、传什么参数**；工具内部怎么匹配是代码写死的。
   所以 LLM 传「Java 开发工程师」，系统就去找这个完整字符串，自然搜不全。
2. **问数量走错了工具**：`search_jobs` 是**语义 Top-k 检索**，`k` 多大就最多几条，**天然答不出"有多少个"**；
   返回总数的是 `filter_jobs`。旧 Prompt 没有把这条路由写清楚。

### 3.3 修复内容

| 层 | 改动 |
|---|---|
| `src/rag/query.py` | 新增 `normalize_text` / `keyword_terms` / `term_hit`：归一化（小写+全角转半角+分隔符统一）→ 中英混排按字符类型切开 → **剥掉泛词**（开发/工程师/高级/资深/技术/相关…）→ 按**核心词**匹配；ASCII 核心词加**词边界**（`java` 命中「java开发」，但**不**命中 `javascript`／`myjava`）；多个核心词按 **AND**（"Java 后端" 不会把纯后端岗算进来），同时给出"任一核心词"的宽口径 |
| `src/rag/query.py` | 命中数改为**分层统计**：岗位名称命中 / **名称或技能标签命中（主口径）** / 含职位描述提及（宽口径）；样例优先给主口径命中的岗位 |
| `src/agent/tools.py` | `filter_jobs` 描述重写（说明核心词匹配 + 三口径）；`search_jobs` 明确标注「**答不了数量**」；返回值带 `命中口径` 与 `解析后的核心词` 便于审计 |
| `src/agent/prompts.py` | 新增规则 5/6/7（见上表），并删除工具清单里重复的 3 行 |

### 3.4 修复后验证

**① 五种写法结果完全一致**（福州，主口径）：

| 传入的 keyword | 解析出的核心词 | 名称 | 主口径 | 含描述 |
|---|---|---|---|---|
| `Java` | `['java']` | 84 | **139** | 228 |
| `Java开发` | `['java']` | 84 | **139** | 228 |
| `Java 开发工程师` | `['java']` | 84 | **139** | 228 |
| `java` / `JAVA` | `['java']` | 84 | **139** | 228 |

**② 与独立真值逐一对齐（8/8 通过）**：`Java`、`Java开发`、`Java 开发工程师`、`java`、`JAVA`、`全栈`、`javascript`、`软件测试` 的「名称/主口径/宽口径」三个数全部与用 pandas 独立统计的真值一致。

**③ 边界情况**：`java` ✅ 命中「java开发工程师」；🚫 不命中「javascript工程师」「myjava工程师」。回归项：福州总数仍为 1,173（未误伤）；单次筛选（含缓存）**0.025s**。

**④ 端到端重跑同一问题**：Agent 现在自己传**核心词 `Java`** 并调用 `filter_jobs`，回答：

> **福州市 Java 岗位：139 个**（主口径：岗位名称或技能标签命中）
> - 岗位名称含「Java」：84 个（严格口径）
> - 名称或技能标签命中：139 个（推荐主口径）
> - 含职位描述提及：228 个（宽口径）
> 参考背景：福州岗位库共 1,173 条，Java 相关岗位约占 **11.9%**（139/1173）。

**从「7 条」到「139 个」，且三个口径都交代清楚。**

## 四、从这一轮迭代得到的结论（写进《大模型应用文档》）

1. **工具粒度决定 Agent 的调用轮数**：把"逐项查询"做成聚合工具（`salary_rank`），比在 Prompt 里反复叮嘱"不要重复调用"更有效。
2. **Prompt 约束要可验证**：把"不许编数字""没查到要直说"写成硬性规则后，示例问答里数字全部带来源，边界问题如实承认未覆盖。
3. **版本号要进缓存键**：否则改完 Prompt 仍会命中旧答案，评估结论会被污染。
4. **Prompt 的约束必须配一个"够得着"的工具**：v2/v3 一直写着「不许用常识代替本系统数据」，但只要结论卡检索不可达，模型就**只能**编——补上 `search_kb` 后，有来源率立刻从 90% 升到 97%，这是本轮收益最大的一条改动。
5. **检索质量是 Agent 能力的上限**：`search_kb` 之所以要单独走「只检索结论卡 + 关闭岗位卡兜底」的路由，正是因为纯语义检索时 16 张结论卡会被 8,836 张岗位卡淹没（任务10 召回评估 P@5 0.147 → 分类型路由 0.353）。**RAG 检索做不好，Prompt 写得再严也没用。**
6. **"工具选对了"不等于"查得全"**（v5 的教训）：v4 已经让 Agent 会挑工具，但**工具内部的匹配逻辑写死了整串子串匹配**，于是"换种说法就搜不到"。**Prompt 只能决定"调哪个工具、传什么参数"，参数进来之后能不能召回全，是工具内部实现的事。** 这条也提醒：评估 Agent 不能只看"有没有调工具"，还要**用真值核对返回的数字**。
