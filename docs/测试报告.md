### 4.5 响应时间基线与优化（任务13）

**方法**：`scripts/bench_api.py` 对 17 个接口分别打 N 轮（慢接口 10~15 轮、快接口 30 轮），每轮先热身一次以触发懒加载，取 P50/P95/P99；结果落盘 `reports/接口性能_baseline.json` 与 `reports/接口性能_after.json`，用 `python scripts/bench_api.py --compare 前 后` 出对比表。

#### 4.5.1 首要一步：先确认"测量本身可信"

把**同一份代码**在同一台机器上测两遍（间隔 20 秒、条件相同），结果差异高达 **47%**：

| 接口 | 第一次 P50 | 同条件重测 P50 | 差异 |
|---|---|---|---|
| 首页聚合 | 19.2 ms | 28.2 ms | **+47%** |
| 岗位统计 | 39.0 ms | 50.3 ms | +29% |
| 公司统计 | 5.9 ms | 9.3 ms | +58% |
| 人岗匹配 Top50 | 282.9 ms | 309.8 ms | +10% |

**结论：本机（笔记本 / 单 worker / CPU 推理）上毫秒级接口的百分比差异不可信**，只有重负载接口（解析 / 匹配 / 评分）的差异才值得解读。后面的对比因此采用**背靠背两次测量**，并且**不把 ≤±10% 的差异称为"优化"**。

#### 4.5.2 背靠背对比（相同条件、间隔 20 秒）

| 接口 | 前 P50 | 后 P50 | 差异 | 前 P95 | 后 P95 |
|---|---|---|---|---|---|
| 简历解析 | 183.7 ms | 186.1 ms | +1% | 199.5 ms | 201.0 ms |
| 人岗匹配 Top50 | 309.8 ms | 311.8 ms | +1% | 412.2 ms | 414.4 ms |
| 双口径评分 | 243.8 ms | 247.3 ms | +1% | 251.5 ms | 311.7 ms |

→ **后端接口耗时无实质变化**。本轮后端改动（聚类画像行数上限、字段类型转换、错误体统一）都不在匹配 / 评分 / 解析的调用路径上，这是预期结果 —— **这里不声称任何后端提速**。

#### 4.5.3 本轮真实且可复现的优化：前端产物体积

整套 Vue 前端只有**岗位详情页的一张六维雷达图**用到 ECharts，但 `web/src/components/EChart.vue` 原来是 `import * as echarts from 'echarts'`（**全量引入**），把约 1MB 的整包打进了该页面的 chunk —— 用户要下完这 1MB 才可能看到雷达图。

改为**按需引入**（`echarts/core` + `RadarChart` + `RadarComponent`/`TooltipComponent`/`LegendComponent`/`TitleComponent` + `CanvasRenderer`）后实测：

| 产物 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `JobView-*.js` 原始 | 1,127.98 kB | 467.59 kB | **−660.39 kB（−58.5%）** |
| `JobView-*.js` gzip | 374.71 kB | 158.07 kB | **−216.64 kB（−57.8%）** |
| 整个 `web/dist` 原始 | 2,801,407 B | 2,141,021 B | **−660,386 B（−23.6%）** |

这是**确定性收益，不受测量噪声影响**（两侧都是真实构建产物：`npm run build` 输出里的原始大小与 gzip 大小）。验证：`npm run typecheck` 0 错误、`npm run build` 成功、`npm run check:render` **8 路由 0 失败 0 控制台错误**（雷达图仍正常渲染）。代码里已写明"以后新增图表类型/组件必须同步 `echarts.use([...])`，否则那张图**静默不渲染**、不报错"。

#### 4.5.4 各候选优化项的处理结论（含未做的与原因）

| # | 候选项 | 处理结论 |
|---|---|---|
| 1 | **前端 ECharts 按需引入** | ✅ **已做**：岗位详情页 JS gzip 374.71 → 158.07 kB |
| 2 | 启动预热 | 已有（`SVC.preload()`：匹配器与 RAG 检索**同步**预加载，实测 2.9~3.4s / 3.7~5.2s；评分特征构造器放**后台线程** 2.2~2.8s，不阻塞启动），本轮无改动 |
| 3 | Nginx gzip + 静态资源长缓存 | 已在任务12 做好（`docker/nginx.conf`：`gzip on`、`/assets` 一年强缓存、`index.html` 不缓存）；**本地没有 Nginx，压缩比无法实测**，留到服务器上用 `docker/verify_deploy.sh` 验收 |
| 4 | `/api/jobs` 筛选列预计算 | **未做**：实测 P50 仅 1.3~4.7 ms，不是瓶颈。做了也测不出收益，属于"为了优化而优化" |
| 5 | `/api/match` 打分向量化 | **未做**：全量 8,836 岗打分 P50 ≈ 310 ms，已远优于课程要求（<3s）；且改动会触及已用 322 项测试与《人岗匹配文档》锁定的口径，收益与风险不成正比 |
| 6 | `/api/companies/stats` 响应体 97 KB | **不在代码层解决**：交给 Nginx gzip（JSON 压缩比通常 5~8 倍），属部署层手段，见第 3 条 |
| 7 | `/api/cluster/profile` 返回 22 行（约 1.2 KB） | 体量很小，无优化必要；本轮只把被截断的 9 条补全（见缺陷 13） |

#### 4.5.5 小结

- **可复现的收益**：岗位详情页首屏要下载的 JS 从 1.1 MB（gzip 375 kB）降到 468 kB（gzip 158 kB），整个前端产物减少 23.6%。
- **后端耗时**：在噪声范围内没有变化，**如实记录，不编造提升数字**。
- **测量本身的教训**：不先做"同条件重测"就下结论，很容易把 20~50% 的机器抖动当成优化成果报出去。

① 公司ID 硬编码 `C0001`（真实ID 形如 `C1875D776`）→ 接口 400；

③ 持久化测试解析的 JSON 键写成了通用的 `items`，而接口返回的是中文键 `简历`/`收藏` → 永远数出 0，把"已保存成功"误报成"数据丢失"。

**还修了 `check:render` 的 4 处时序弱点**（它原来是按本机速度写的，对着 2 核云服务器会假失败）：
固定 `sleep(1600)` 改为"等期望文本出现（上限 20 s，可用 `WAIT_MS` 覆盖）"、点岗位卡前先等 `.jcard` 渲染、
坐标点击改 DOM 点击（拖动测试把悬浮球挪到页面中部，会盖住卡片 —— 实测卡片中心最上层是 `el-loading-mask`）、
读列表改"连续两次读取一致才算稳定"。**修完本地与公网都全绿**。

> **附：一次差点被误判为"应用 bug"的排查（值得记）**
>
> 修完上面 4 处后，"翻页出现重复岗位 1 条"仍以**约 1/3 的概率**复现。当时的第一反应是"应用的分页有 bug"，
> 于是抓了每次 `/api/jobs` 请求的参数：
> ```
> 请求：page=1 seed=209634161 ｜ page=2 seed=209634161   ← 种子完全相同
> 第1页首条「HRBP」  第2页首条「资金管理专员」   重复 1 条：["测试工程师"]
> ```
> 读了实现才确认**分页本身没问题**：`JobStore.query` 里是 `rows = list(rows)` 先复制再 `random.Random(seed).shuffle(rows)`，
> 同一个种子对同一个输入顺序必然产生同一个排列，第 1、2 页按 ID 绝不相交。
> 真正的原因是**断言拿"岗位名称"当唯一标识**：8,836 个岗位里只有 **6,037 个不同名称，41.2% 的岗位重名**
> （「测试工程师」**67** 个、「品质工程师」**52** 个）。两个不同岗位恰好同名，就被算成了"重复"。
>
> **修法**：给岗位卡片加 `data-id="岗位ID"`，断言改成按 **ID** 比较 —— 现在按 ID 零交集。
>
> **教训**：**"看起来像 bug"的现象，先看断言用的标识是不是唯一的**。
> 用业务名称做跨集合比较，在真实数据（重名率 41%）上必然产生假阳性；
> 而且这种假失败很有迷惑性 —— 它会稳定地以一定概率出现，看起来完全像一个真实的偶发缺陷。
