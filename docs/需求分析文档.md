## 1. 选题背景与项目定位

### 1.1 背景
传统招聘中，"海投简历 + 人工筛岗"效率低、双方信息不对称：
- 求职者：不清楚自己与岗位的匹配程度，投递命中率低；
- 招聘方：简历量大，人工筛选成本高、标准不一。

### 1.2 项目定位
采集**招聘平台公开岗位数据**，围绕**简历**构建一个人岗匹配推荐系统：
> 输入一份简历 → 输出「匹配评分 Top-N 岗位推荐 + 岗位聚类画像 + 智能问答」。
> 让"找什么工作、岗位是否合适、为什么合适"三个问题有据可依。

### 1.3 系统边界（本期不做）
- 不做在线投递/简历解析服务，不做双向社交功能；
- 简历输入本期以「文本粘贴 / PDF 提取」为主；
- 数据仅用于教学实训，非商业用途。

## 3. 业务问题拆解（四问对齐课程主线）

课程要求围绕"评分 / 匹配 / 聚类 / 大模型"四个业务问题展开，映射如下：

| 业务问题 | 用户诉求 | 输入→输出 | 技术方案 | 评估指标 |
|---------|---------|----------|---------|---------|
| ① 岗位质量评分 | 这份工作"好不好/值不值得投" | 岗位字段 → 质量分(0-100) | 特征工程 + Logistic/SVM/RF/XGBoost | 准确率/F1、可解释性 |
| ② 人岗匹配 | 我适合什么岗位/岗位适合我吗 | 简历+岗位 → 匹配度分、Top-N推荐 | 技能 TF-IDF+余弦 + 加权匹配公式 | 召回Top-k命中、样例人工核验 |
| ③ 岗位聚类画像 | 岗位分成哪几类、我属于哪类 | 岗位特征 → 簇标签+画像 | K-Means(肘部法/轮廓系数) + PCA/t-SNE | 轮廓系数、簇命名可读性 |
| ④ 大模型问答 | 自然语言问岗位/求职建议 | 问题 → 带溯源的答案+推荐 | RAG(向量库) + Agent(Function Calling) | 召回Top-k、溯源正确率 |

> **评分模型（①）与匹配模型（②）的关系**：①回答"岗位本身质量"，②回答"岗位与我的适配度"，二者共同进入推荐排序。

## 4. 用户角色与典型场景

### 4.1 用户角色
1. **求职者（主用户）**：应届生/社招人群，需快速定位合适岗位；
2. **招聘分析师 / HR（次用户）**：观察岗位市场分布（薪酬、城市、行业聚类）。

### 4.2 典型场景（故事化）
- 场景A：应届生小张粘贴简历，系统给出 80 分的「数据分析师」岗位并说明：技能相似度 0.72、学历符合、经验差 1 年——为什么匹配；
- 场景B：HR 想了解"北京 Java 岗薪酬分布"，用自然语言提问，系统检索岗位库给出带来源的统计回答；
- 场景C：求职者浏览"岗位族谱"，看到系统把岗位聚成「研发/数据/产品/运营/职能」等画像簇，了解市场结构。

## 5. 数据源选定与采集方案（任务2 前置设计）

### 5.1 数据源对比结论

| 数据源 | 优点 | 缺点 | 结论 |
|--------|------|------|------|
| **前程无忧51job** ✅ | 分页规整、字段全（薪资/经验/学历/描述）、反爬较温和、requests 可抓 | 部分字段需解析清洗 | **主数据源** |
| BOSS直聘 | 数据新 | 强反爬、需登录、动态渲染 | 备选（需 Selenium/Playwright） |
| 智联/猎聘 | 岗位质量高 | 字段解析成本中高 | 备选 |
| 开源数据集/模拟数据 | 无爬取风险 | 非实时、需人工核验真实性 | 兜底（若主源失败） |

### 5.2 采集目标
- **总量 ≥ 1 万条**（课程硬性要求）；
- 覆盖 3-5 个核心城市 + 多行业 + 技术/非技术岗位，保证聚类有意义；
- 分页抓取，落盘 `data/raw/`，保留原始字段一份 + 规整字段一份。

### 5.3 岗位字段表设计（原始→规整字段映射）

| 规整字段 | 含义 | 来源/解析方式 | 示例 |
|---------|------|--------------|------|
| job_id | 岗位唯一ID（去重键） | 详情页/链接解析 | 12345678 |
| job_title | 职位名称 | 页面标题 | 数据分析师 |
| company | 公司名称 | 公司区 | XX科技 |
| industry | 所属行业 | 行业字段 | 互联网/电子商务 |
| city / district | 城市/区域 | 工作地点 | 北京 / 海淀 |
| salary_text | 薪资原始文本 | 页面 | 1.5-2万/月 |
| salary_min/max/avg | 薪资解析数值(元/月) | 正则解析 | 15000 / 20000 / 17500 |
| exp_required | 经验要求原始文本 | 页面 | 3-4年经验 |
| exp_min | 经验要求数值(年) | 正则解析 | 3 |
| education | 学历要求 | 页面 | 本科 |
| description | 职位描述（核心文本） | 详情 | …(含职责+技能词) |
| welfare_tags | 福利标签 | 页面 | 五险一金,带薪年假 |
| publish_date | 发布日期 | 页面 | 2026-09-05 |
| url | 来源链接（溯源用） | 页面 | … |
| crawl_time | 采集时间 | 程序 | 2026-09-08 10:00 |

### 5.4 反爬与合规策略
- 随机 User-Agent、两次请求间随机延时（如 2-5s）、失败指数退避重试（≤3 次）；
- 单城市单页并发适度，遵守 robots.txt 与服务条款，仅采集公开信息；
- **明确不采集**求职者简历等个人敏感信息；测试用简历一律脱敏/模拟生成。

### 5.5 兜底方案
若 51job 限流严重导致 3 天内数据不足 1 万条：切换城市/关键词继续抓取，
或启用智联备选源；最终仍不足则用开源招聘数据集补充并在文档中声明来源。

### 6.2 非功能性需求（NFR）
- **数据量**：有效岗位数据 ≥ 1 万条（清洗去重后统计口径写入预处理文档）；
- **性能**：接口响应（推荐 Top-10）本地 < 3s；RAG 检索 < 2s；
- **可解释性**：匹配分必须能拆解为各维度得分并给出文字理由；
- **可复现性**：随机种子固定、代码与数据版本对应、文档记录全部口径；
- **规范性**：全程 Git 记录，最终答辩核验提交历史；代码有注释与 README。

## 7. 系统总体方案设计

### 7.1 数据流（端到端管道）
```
[51job 网页] ──爬虫(任务2)──▶ data/raw/ ──清洗特征(任务3)──▶ data/processed/
                                                            │
        ┌───────────────────────────────────────────────────┤
        ▼                                                    ▼
  [可视化分析(任务4)]                              [特征库: 技能/薪资/经验/学历/城市]
        │                                                    │
        ▼                        ┌───────────────────────────┤
  ≥6张图+洞察报告             ▼            ▼                ▼
                     评分模型(任务5)  匹配模型(任务6)  聚类模型(任务7)
                          │            │                │
                          └──────┬─────┴───────┬────────┘
                                 ▼             ▼
                       [FastAPI 服务(任务11)]  [岗位向量库→RAG(任务10)]
                                 │             │
                                 ▼             ▼
                    [简历输入: 粘贴/PDF]      [Agent 对话(任务10)]
                                 └──────┬──────┘
                                        ▼
                              [推荐结果 + 理由 + 溯源]
                                        ▼
                              [Streamlit/Vue3 前端(任务11)]
                                        ▼
                              [Docker 部署上线(任务12)]
```

### 7.2 技术栈选型
| 环节 | 选型 | 理由 |
|------|------|------|
| 爬虫 | requests + BeautifulSoup4（动态页备 Selenium） | 51job 静态分页为主，轻量可控 |
| 数据处理 | pandas + numpy + jieba | 中文分词、表格处理标准栈 |
| 可视化 | matplotlib + seaborn | ≥6张业务图 |
| 机器学习 | scikit-learn（TF-IDF/Logistic/SVM/RF/K-Means/PCA）+ xgboost | 课程指定模型全覆盖 |
| 匹配 | TF-IDF + 余弦相似度 + 自定义加权公式 | 可解释性优先于黑盒 |
| 向量库 | Chroma（备 FAISS/Milvus） | 本地轻量起步，容量不足再迁移 |
| 大模型 | OpenAI 协议 SDK / 通义 qwen（Key 放 .env 不入库） | Function Calling 支持成熟 |
| 后端 | FastAPI + uvicorn | 四类 API（评分/匹配/聚类/对话） |
| 前端 | Streamlit（备 Vue3） | 快速演示、3天集成时间紧 |
| 部署 | Docker + docker-compose + 云服务器 | 课程指定 |
| 版本控制 | Git + GitHub（zhengqing798/zq） | 团队协作 + 答辩核验 |

### 7.3 人岗匹配方案预设计（任务6 预告）
匹配分 = `w1·技能相似度 + w2·学历匹配 + w3·经验匹配 + w4·薪资匹配 + w5·城市匹配`，
其中技能相似度 = 简历技能词集与岗位技能词集的 TF-IDF 加权余弦相似度；各 w 初始可设为
0.4/0.2/0.2/0.1/0.1，最终在任务6中以样例调优并记录版本。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 51job 反爬限流/封IP | 数据不足1万条 | 随机UA+延时+重试；多城市多关键词；备用数据源兜底 |
| 数据量不足或分布偏斜 | 模型/聚类无说服力 | 3-5城+多行业覆盖；清洗统计口径提前定 |
| 薪资/经验文本格式乱 | 特征工程难 | 正则+枚举归一化，人工抽检100条标注口径 |
| 大模型 API 费用/限流 | RAG/Agent 演示失败 | 用 qwen-turbo 等低成本模型；本地向量库做检索主链路，LLM 只做生成 |
| 时间紧（3周集中） | 进度失控 | 每天按课程表交付；Git 每日提交；预留周五缓冲 |
