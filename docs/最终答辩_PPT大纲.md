## 三、第二段：建模进阶与大模型应用（第 2 周 · 任务6–8、10）

### P11 任务6：人岗匹配（技能用 TF-IDF + 余弦）
- 六维匹配：**技能 / 经验 / 学历 / 地域 / 薪资 / 专业证书**
- 技能维度 = **TF-IDF + 余弦相似度** + 技能词典命中率融合
- 权重两版对比：v1 `0.30/0.20/0.15/0.15/0.12/0.08`（任务5 标签口径）→ v2 `0.38/0.18/0.12/0.16/0.10/0.06`（在线推荐口径，经 200 份简历调优，**大类一致率 +4.40pp**）
- 输出：Top-N 岗位 + **六维分明细** + **中文推荐理由**；全量 8,836 岗打分 **0.17 s**（课程要求 <3s）
- 产出：`docs/人岗匹配文档.md` ｜ 配图：匹配结果卡截图（含六维雷达图）｜ ⏱ 75 秒

### P12 任务7：岗位聚类（K-Means）
- 定 K：**肘部法 + 轮廓系数**双判据 → **K=9**（轮廓 **0.6735**，ARI **1.0000**）
- 降维可视化：**PCA + t-SNE**
- 簇命名 + **业务解读**：最大簇「制造业质量/检验」占 **51.45%**（说明岗位库构成偏制造业，且簇内异质）
- 进阶：对 51.45% 的"其他"巨簇做**二阶细分（K=8）**
- 配图：肘部法曲线 + PCA/t-SNE 分布图 + 簇画像表 ｜ ⏱ 70 秒

### P13 任务8：多模型对比
- 对比对象：**评分模型（模型口径）× 匹配规则（规则口径）× 聚类结果**
- 量化结论：两套口径的 Top-N 推荐 **Jaccard 相似度 0.788**、**Spearman 秩相关 0.9909** → **规则与模型高度一致，互为佐证**
- 诚实结论：不一致的部分集中在"技能命中少但综合条件好"的岗位，两种口径各有适用场景
- 产出：`docs/多模型对比分析报告.md` ｜ ⏱ 60 秒

### P14 任务10-1：RAG 知识库构建
- 卡片化：**8,852 张知识卡 = 8,836 张岗位卡 + 16 张结论卡**
- Embedding：**BAAI/bge-small-zh-v1.5**（512 维，[CLS] 向量 + L2 归一化，CPU 推理）
- 向量库选型：**FAISS `IndexFlatIP`**（余弦检索）
  - **为什么不用 Chroma**：课程要求"选向量库"，我们三个都评估了；Chroma 跨进程重载会报 hnsw 索引错误，而本场景只有 8,852 条 × 512 维（**17 MB，一次矩阵乘约 30 ms**），进程内 FAISS 更简单也更快 —— **选型理由写进了《大模型应用文档》**
- ⏱ 70 秒

### P15 任务10-2：召回评估（30 问 × 3 模式）
- 评估方式：**30 条真实问题**，逐条记录 Top-k 命中与来源，产出三元组

| 模式 | P@5 | R@5 |
|---|---|---|
| 纯语义检索 | 0.147 | 0.667 |
| + 卡片类型路由 | 0.340 | 0.860 |
| + 城市过滤 | **0.353** | **0.873** |

- 关键发现：**纯语义检索时，16 张结论卡被 8,836 张岗位卡淹没**（P@5 仅 0.147）→ 这就是后来加 `search_kb` 专用工具的直接动因
- 溯源：**30 问有来源标注 30/30**
- ⏱ 70 秒

### P16 任务10-3：Agent 智能体与工作流编排
- **DeepSeek Function Calling** + **12 个工具**：岗位检索 / 筛选 / 薪资统计 / 城市薪资排名 / 城市清单 / 人岗匹配 / 聚类画像 / **结论卡检索** / 知识库自述 / **通用分组统计** / **公司维度** / **榜单统计**
- 工程约束：最多 **6 轮**、**12 次**工具调用、工具结果回灌上限 10,000 字符、**7 天缓存 TTL**、多轮追问带最近 6 轮上下文
- 编排形态（30 问实测）：**70% 的问题 2 次工具调用内解决**，典型序列 `search_kb → filter_jobs`（即"**先取口径、再取数据**"）
- 演示价值：**这不是代码写死的流程，是模型每次现场决策的结果**
- ⏱ 75 秒

### P17 任务10-4：Prompt 版本管理与迭代（课程硬指标）
- 版本链：**v1 设计稿 → v2 落地 7 条约束 → v3 加聚合工具 → v4 加结论卡检索 → v5 修检索口径 → v6 扩到 12 工具 → v7 要求给岗位链接**
- 三次**最有说服力**的迭代（每次都有前后实测数字）：

| 迭代 | 问题 | 结果 |
|---|---|---|
| v2→v3 | 问"薪资最高的城市"时模型逐城调 12 次、撞上限 | 工具调用 **12 → 2 次**，tokens **9,330 → 4,182**，耗时 7.1s → **3.8s** |
| v3→v4 | 30 问中 **3 条完全不调工具**（用行业常识答本系统口径） | 有来源率 **90% → 97%**；不用工具的问题 **3 → 1** |
| v4→v5 | 用户实测：「福州 Java 岗位有多少」只召回 **7 条**（实际 139 个） | 匹配层重写 + 数量口径修正；`Java`/`java`/`Java开发` 五种写法**结果完全一致**，**7 条 → 139 个** |

- **结论金句**（建议作为这一页的收尾）：**"Prompt 里写『不许编数据』，但如果不给它一个够得着的工具，等于逼模型说谎。"**
- 产出：`docs/prompt版本记录.md` ｜ ⏱ 90 秒

### P19 任务11：功能链路与用户体系
- 四条链路全部打通（课程要求的"上传简历→匹配→推荐→对话"）：
  1. 简历输入：**粘贴文本 / 上传 PDF** 两条通路共用同一解析器（字段回归 **100%，80/80**）

### P20 任务12：容器化（镜像分层 + 编排）
- **后端镜像六层**：系统层 → 依赖层 → 向量模型层 → 数据层 → 代码层 → 运行期配置
  - 效果：**只改代码时，依赖/模型/数据三层全部命中缓存**，重建从十几分钟降到几秒
- **前端镜像两阶段**：Node 构建 → Nginx 运行（只把构建产物搬进运行镜像）
- **compose 双容器**：`web`（Nginx，对外 80）+ `api`（FastAPI，**仅内网**，`depends_on: service_healthy`）
- **为什么只有两个容器（评委很可能问）**：检索是 FAISS **进程内**索引（17 MB / 一次矩阵乘 30ms），拆成独立向量库只多一次网络往返、毫无收益；sqlite 单文件挂卷比引入 MySQL 更划算 —— **值得独立成容器的是"有状态且需独立扩缩"的组件，本项目只有 Nginx**

1. **每页只讲一件事**：15~20 分钟 / 29 页 ≈ 40 秒/页；数字墙（P3）、Prompt 迭代（P17）、缺陷（P24）、性能（P25）可以多给 20 秒。
