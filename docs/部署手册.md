## 二、容器架构

```
                      公网
                       │  80
             ┌─────────▼──────────┐
             │  web  (Nginx)      │   镜像 zq-web:1.0.0，几十 MB
             │  · 托管前端静态产物 │
             │  · /api → 反代      │
             │  · gzip / 长缓存    │
             └─────────┬──────────┘
                       │  compose 内网，服务名 api:8000
             ┌─────────▼──────────┐
             │  api  (FastAPI)    │   镜像 zq-api:1.0.0，约 2GB
             │  岗位库 8,836       │   ● 只暴露内网端口，公网进不来
             │  六维匹配 / XGBoost │   ● 挂卷 zq-var → /app/var
             │  RAG 向量检索       │   ● healthcheck: GET /api/health
             │  DeepSeek Agent     │
             └─────────┬──────────┘
                       │
                 ┌─────▼─────┐
                 │ 卷 zq-var │  用户 / 简历 / 收藏 / 匹配历史 / Agent 缓存
                 └───────────┘
```

### 为什么是这两个容器（而不是硬凑数量）

- **向量库不单独成容器**。项目用的是 FAISS `IndexFlatIP` 进程内检索：8,852 条 × 512 维只占 17MB，一次矩阵乘约 30ms。拆成独立服务只会多一次网络往返和一份向量序列化开销，没有任何收益。早期占位文件里写的 `chromadb/chroma` 容器**实际未采用**（评估结论见《大模型应用文档》，chromadb 跨进程重载会报 hnsw 索引错误）。
- **数据库不单独成容器**。sqlite 单文件放在数据卷 `/app/var/app.db`，对这个量级（几百用户、几千条简历）比引入 MySQL/Postgres 更划算，也少一个故障点。
- **真正值得独立成容器的是"有状态 + 需要独立扩缩"的组件**，本项目只有 Nginx 这一个（静态资源与 TLS 终止不该和应用进程抢资源，也不该跟着应用一起重启）。
- 什么时候才需要第三个容器：把 Agent 会话态/结果缓存改成多实例共享。本期用「进程内内存 + 磁盘缓存 + 数据卷」已经够用；真要扩到多副本，再引入 redis 即可，不需要改镜像。

### 前端为什么能和后端同源

前端 `web/src/api/client.ts` 里 `baseURL: import.meta.env.VITE_API_BASE || ''`（默认空），所有请求都是相对路径 `/api/*`；开发期靠 Vite 代理，生产期靠 Nginx 反代。所以**不需要配置任何后端地址，也没有跨域问题**。

## 三、镜像设计

### 3.1 后端镜像的六层（`docker/Dockerfile`）

| 层 | 内容 | 为什么单独一层 |
|----|------|----------------|
| ① 系统层 | `curl`（healthcheck 用）+ `tini`（正确转发信号）、时区、UTF-8 | 几乎不变 |
| ② 依赖层 | `requirements.torch.txt` + `requirements.lock.txt` | 只在依赖变更时重装 |
| ③ 向量模型层 | 构建期从 hf-mirror 下载 `BAAI/bge-small-zh-v1.5` | 92MB 二进制，与代码无关 |
| ④ 数据层 | `data/` + `models/` | 约 190MB 只读资产，改动频率远低于代码 |
| ⑤ 代码层 | `src/` + `scripts/` + `tests/` + `pytest.ini` | 改代码只重跑这一层 |
| ⑥ 运行期配置 | 非 root 用户、`/app/var` 可写目录、`HEALTHCHECK`、`CMD` | — |

**效果**：只改 `src/` 里的 Python 代码时，②③④ 三层全部命中缓存，重建只要几秒，不会为了改一行代码重新下载约 300MB 依赖（实测依赖总下载量 0.28 GB）。

### 3.2 关键取舍与理由

| 取舍 | 决定 | 理由 |
|------|------|------|
| worker 数量 | `--workers 1` | 岗位库 / FAISS 索引 / XGBoost 模型都是进程内单例，实测常驻约 0.9GB；多 worker 让内存翻倍而收益有限。本项目瓶颈是 CPU 推理而非 IO，并发交给 uvicorn 的异步循环 + 线程池 |
| torch | 走 `download.pytorch.org/whl/cpu` | PyPI 上 Linux 的 torch 是 CUDA 构建，会额外拖进约 2.5GB 的 `nvidia-*` 依赖，而本项目只用 CPU 推理 |
| `nvidia-nccl-cu13` | 装完立刻卸掉 | `xgboost 3.4.1` 的元数据在 Linux 上**无条件**依赖它（`platform_system == "Linux"`），而它是 CUDA 集合通信库，单个 wheel **240.7 MB**。依据：xgboost 的 Python 代码完全不 import 它，同一版本在本机 Windows 上根本没装这个包、导入与训练都正常。安装与卸载放在同一层，文件不会留在镜像里（`ARG STRIP_GPU_LIBS=1` 可关掉） |
| 向量模型 | 构建期下载进镜像 + 运行期 `HF_HUB_OFFLINE=1` | 容器里没有模型缓存时，第一次问答会现场去 huggingface 拉 92MB，国内网络下必然超时。烘进镜像后容器**完全不需要外网** |
| 依赖来源 | 锁定清单而不是 `requirements.txt` | `requirements.txt` 写的是 `>=` 区间，几周后 `docker build` 装到的版本可能就不是本地验证过的那套了 |
| 非 root | `USER appuser` | 容器被攻破也拿不到 root |
| 密钥 | 只在运行时由 compose 注入 | 镜像里没有 `.env`，任何一层都取不到 Key；`.dockerignore` 已双重排除 |
| 测试代码 | 打进镜像 | 任务要求「本地验证」，镜像内能直接跑 **322 项** pytest 是"镜像内依赖完整"最直接的证据。代价可忽略（几百 KB） |

### 3.3 前端镜像

两阶段：`node:22-alpine` 里 `npm ci` + `npm run build` 产出 `dist`，再 `COPY` 进 `nginx:1.27-alpine`。只把构建产物搬进运行镜像，源码不进。

### 3.4 不写 `.dockerignore` 会怎样

`web/node_modules` 有 232MB、`.venv` 也有上百 MB，都会在每次构建时传给 Docker daemon；更严重的是 `.env`（大模型密钥）与 `data/app.db`（本机用户账号与密码哈希）会被 `COPY` 进镜像层。所以 `.dockerignore` 不是可选项。

## 四、构建期排掉的坑（都有实证）

写 Dockerfile 的过程里踩到 5 个问题，其中 3 个是**项目里早就存在、只是没被触发**的缺陷：

| # | 问题 | 症状 | 处理 |
|---|------|------|------|
| 1 | `requirements.txt` 缺编码声明 | `pip install -r requirements.txt` 在中文 Windows 上直接崩：`UnicodeDecodeError: 'gbk' codec can't decode byte 0x80` | 查 pip 源码 `pip/_internal/utils/encoding.py`，它只按 BOM / PEP 263 前两行声明探测编码，都没有就退回系统区域编码（中文 Windows 是 GBK）。在文件首行加 `# -*- coding: utf-8 -*-` |
| 2 | 直接用 `pip freeze` 当锁定清单 | 会把机器上一堆与本项目无关的包（`chromadb`、`nameko`、`eventlet`、`cvxopt`…）也钉进镜像 | 改成以 `requirements.txt` 顶层依赖为起点**递归求已安装依赖闭包**，清单从 209 个降到 **88 个** |
| 3 | `cvxopt==1.3.3` 被报"无可用 wheel"（误报） | Linux 预检失败 | 实为检查方法错了：`--platform manylinux2014_x86_64` 只接受 glibc ≤ 2.17 的 wheel，会拒掉 Debian 12 上合法的 `manylinux_2_28` |
| 4 | `faiss-cpu==1.15.0` 被报"无可用 wheel"（误报） | 同上 | 实为 `--abi cp312` 只认 cp312 标签，而 faiss 发的是 `cp310-abi3`（稳定 ABI，cp312 兼容），被误判 |
| 5 | `xgboost` 在 Linux 拖进 240.7MB 的 CUDA 库 | 镜像白胖 240MB | Dockerfile 里装完即卸（见 3.2） |

第 3、4 条值得单独说：**第一版检查脚本还把 59 个纯 Python 包也误报成"没有 Linux wheel"**，原因是我漏了 `py3-none-any` 里的平台标签 `any`。所以最后改成 `scripts/check_linux_wheels.py`，自己查 PyPI 文件清单、按明确规则判定（Python 标签兼容 ∧ 平台标签兼容 glibc ≤ 2.36），逻辑完全可控 —— **检查工具本身也验证过一遍**。

## 五、本地验证

### 5.1 为什么分两半做

任务要求「构建镜像并本地验证」。本机没装 Docker（也没有 WSL Linux 发行版），所以拆成：

- **这一半现在做**（`scripts/verify_runtime_contract.py`）：与 Docker 无关、但同样决定"镜像能不能跑起来"的部分，在宿主机上**逐条复刻镜像里的运行约定**验证。
- **另一半在服务器上做**（`docker/verify_deploy.sh`）：真正的 `docker build` / `docker compose up`。
- **不做的部分会明说**：镜像的层缓存、构建耗时、镜像体积只能实测，不会用估算冒充实测（见 5.4 与第十节）。

### 5.2 等价验证结果（`python scripts/verify_runtime_contract.py`）

| # | 验证项 | 结果 |
|---|--------|------|
| 1 | 三个依赖清单都能被 pip 正确解析（含编码陷阱回归） | 通过 |
| 2 | `.dockerignore` 里 4 条关键排除项齐全（`.env` / `data/app.db` / `web/node_modules` / `.venv`） | 通过 |
| 3 | `APP_DB` / `AGENT_CACHE` / `AGENT_LOG` 三个环境变量生效，均指向可写卷目录 | 通过 |
| 4 | 按镜像 `CMD` 的完整参数启动后端并能就绪 | 通过 |
| 5 | 8 个关键接口全部 200（首页/岗位/公司/聚类/详情/解析/匹配/评分） | 通过 |
| 6 | 运行期数据落入可写目录（对应容器里的挂卷 `/app/var`） | 通过 |
| 7 | **离线加载 BGE 向量模型并检索出结果**（`HF_HUB_OFFLINE=1`，证明容器无外网也能问答） | 通过，命中 5 条，3.5s |

> 说明：这一轮跑出来过 4/5（第 4 项失败），原因是启动参数里 `--forwarded-allow-ips *` 的**独立 `*` 被通配展开**成整个目录的文件名列表，uvicorn 报 `Got unexpected extra arguments (docker docs models …)` 直接退出。改成等号附着式 `--forwarded-allow-ips=*` 后通过，Dockerfile 里也同步改成附着式写法。

### 5.3 依赖可安装性预检（`python scripts/check_linux_wheels.py`）

- 88 个钉住的包在 `python:3.12-slim`（Debian 12 / glibc 2.36 / x86_64）上**全部可安装**；
- **镜像里不需要任何编译器**（不必装 gcc，镜像更小、构建更快）；
- 依赖总下载量实测 **0.28 GB**（torch 走 CPU 专用源，不是 PyPI 上那个 864MB 的 CUDA 版）；
- 9 个包只有源码包（`jieba`、`openpyxl`、`pytz`、`six`、`python-dateutil`、`colorama`、`pydeck`、`toml`、`tzdata`），但都是纯 Python，pip 的构建隔离会自动装 `setuptools` 打包，不需要 gcc；
- 脚本还会单独列出"只在 Linux 生效的依赖"，用来盯住第 4 节第 5 条那类问题不再复发（当前就一条：`xgboost → nvidia-nccl-cu13`）。

### 5.4 本地无法验证、必须等服务器的部分

| 项 | 为什么本地做不了 |
|----|------------------|
| `docker build` 是否成功、耗时多久 | 没装 Docker |
| 镜像实际体积、各层体积 | 同上 |
| `docker compose up` 后两容器健康状态 | 同上 |
| 从公网 IP 访问、安全组是否放行 | 需要云服务器 |
| 数据卷 `down`/`up` 后数据是否仍在 | 同上 |
| Nginx gzip 实际压缩比 | 需要真的过 Nginx |

## 六、docker-compose 用法

在仓库根目录执行：

```bash
# 构建并启动（首次约 5~15 分钟，取决于网速）
docker compose -f docker/docker-compose.yml up -d --build

# 看状态（api 会显示 healthy）
docker compose -f docker/docker-compose.yml ps

# 看日志
docker compose -f docker/docker-compose.yml logs -f api
docker compose -f docker/docker-compose.yml logs --tail 50 web

# 重启后端（改完代码重建后）
docker compose -f docker/docker-compose.yml up -d --build api

# 停止（保留数据卷）
docker compose -f docker/docker-compose.yml down

# 停止并删除数据卷（会清空用户/简历/收藏）
docker compose -f docker/docker-compose.yml down -v
```

启动后：

| 地址 | 说明 |
|------|------|
| `http://<服务器IP>/` | 前端首页（唯一对外入口） |
| `http://<服务器IP>/docs` | FastAPI 交互文档（验收时演示接口用） |
| `http://<服务器IP>/api/health` | 健康检查（含各组件预加载耗时） |

**后端端口 8000 不对外暴露**（compose 里用的是 `expose` 而不是 `ports`），只能通过 Nginx 的 `/api` 访问。

## 七、云服务器部署

### 7.1 服务器怎么选

| 项 | 要求 | 说明 |
|----|------|------|
| 内存 | **4GB 起**（2GB 会 OOM） | 实测后端常驻 **705MB**（只加载岗位库）→ 全接口跑完 **905MB**；系统 + Docker 自己还要 300~400MB。2GB 机器必须加 swap 才能勉强跑，不建议 |
| CPU | 2 核 | 构建 torch 时会有一次较重的解包 |
| 磁盘 | 40GB 起 | 镜像约 2GB + 构建缓存 + 系统 |
| 系统 | Ubuntu 22.04+ / Debian 12+ | `deploy.sh` 的安装步骤按 Debian 系写 |
| **容器运行时** | **必须是 Linux 机器 + 能跑 Linux 容器** | 镜像基于 `python:3.12-slim`，Windows 容器跑不了；且当前用户需有权限启动 Docker（见 **7.1.1** 的真实踩坑记录） |
| 安全组 | 放行 **22** 与 **80** | 云厂商默认只开 22，80 必须手动放行，否则公网打不开 |

**关于备案**：直接用 `http://公网IP/` 访问**不需要备案**（备案是针对域名解析的）。本课程演示用 IP 即可。

获取途径（具体价格以官网为准）：阿里云「飞天加速计划」学生认证可免费领取 ECS；腾讯云学生机、轻量应用服务器常有 10 元/月档位；新用户轻量特惠常见 2核4G。

### 7.2 一键部署

```bash
# 1) 把代码放到服务器
git clone <仓库地址> zq && cd zq

# 2) 一键部署（自动装 Docker、构建、启动、自检、最后打印在线地址）
bash scripts/deploy.sh

# 想先注入密钥再跑：
DEEPSEEK_API_KEY=sk-你的key bash scripts/deploy.sh

# 想换端口（例如 80 被占用）：
PORT=8080 bash scripts/deploy.sh
```

`deploy.sh` 会依次做 6 件事：环境自检（内存/磁盘/是否在仓库根目录）→ 装 Docker Engine + compose 插件（走阿里云镜像源）→ 准备 `.env` → 构建镜像 → 启动容器 → 轮询 `/api/health` 并逐个打 9 个关键接口做自检，最后打印在线演示地址。

### 7.3 手动部署（想自己控制每一步时）

```bash
# 1) 装 Docker（Ubuntu/Debian）
sudo apt-get update && sudo apt-get install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://mirrors.aliyun.com/docker-ce/linux/ubuntu/gpg | sudo tee /etc/apt/keyrings/docker.asc > /dev/null
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] \
https://mirrors.aliyun.com/docker-ce/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker

# 2) 配置密钥（.env 不进仓库、不进镜像）
cp .env.example .env && vi .env

# 3) 构建并启动
docker compose -f docker/docker-compose.yml up -d --build

# 4) 验收
bash docker/verify_deploy.sh
```

### 7.4 把镜像搬到服务器（服务器拉不动 GitHub 或依赖源时）

```bash
# 本地
docker save zq-api:1.0.0 zq-web:1.0.0 | gzip > zq-images.tar.gz
scp zq-images.tar.gz user@<服务器IP>:~/

# 服务器
gunzip -c zq-images.tar.gz | docker load
cd zq && docker compose -f docker/docker-compose.yml up -d
```

### 7.1.1 先确认「这台机器到底能不能跑 Linux 容器」—— 一次真实踩坑记录

「云服务器」这个词很容易让人以为随便一台都行。实际项目里拿到的第一台是**阿里云 DevBox（Windows Server 2022）**，
在上面折腾了一轮才发现根本跑不了本项目的 Linux 镜像。把排查过程记下来，避免重复踩：

| 检查项 | 命令 | 实测结果 | 为什么致命 |
|---|---|---|---|
| 操作系统 | `uname -a` / `ver` | **Windows Server 2022 Datacenter** | 本项目镜像是 `python:3.12-slim`（Linux），只能跑在 Linux 容器里 |
| Docker 守护进程 | `docker version` | CLI 与 `dockerd.exe` 都在，但连不上 `npipe://./pipe/docker_engine` | 服务没启动，Docker 完全不可用 |
| 是否管理员 | `whoami /groups` / `Get-Service` | **不是管理员**，`Get-Service` 报"需要提升权限" | 起不了 docker 服务、也启用不了容器功能 |
| Linux 容器支持 | `wsl -l -v`、`Get-WindowsOptionalFeature` | **无 WSL、无 Hyper-V、无 Docker Desktop** | 即便有管理员权限，Windows 上也只会是 **Windows 容器**，跑不了 Linux 镜像 |
| compose 插件 | `docker compose version` | `unknown command: docker compose` | 编排脚本也用不了 |
| **入站端口** | 从外部 `Test-NetConnection <IP> -Port 80` | **只有 22 通，80/443/8000 全部不通** | 就算服务跑起来，公网也访问不到（安全组只放了 SSH） |
| 运行时 | `python --version` / `node --version` | 两个都没装 | 想"原生跑"还得先自己装运行时 |
| 资源 | — | 2 核 / 内存 **3.86 GB（空闲 1.84 GB）**/ C 盘剩 25 GB | 本项目 API 常驻约 0.9 GB，能跑但很紧 |
| 外网 | `curl -o /dev/null -w '%{http_code}'` | github / 清华源 / hf-mirror 都 200 | 唯一的好消息：机器上能装东西 |

**结论与教训**：

1. **买/领之前先把「是不是 Linux + 有没有管理员 + 安全组放不放行 80」这三件事确认掉**，比装好之后才发现要省事得多。
2. 第 6 条最容易被忽略：**服务跑起来 ≠ 公网能访问**。安全组默认只开 22，80 必须手动放行。
3. 如果确实只能用这种受限环境，还有一条退路：不用 Docker，改为**原生部署 + 反向隧道**（例如 Cloudflare 隧道），
   由隧道把本机端口暴露成公网 HTTPS 地址，从而绕开「入站端口没开」的限制。代价是地址是临时的、依赖隧道进程常驻，
   而且**「Docker 容器化部署」这条交付就没真正落到云上**，需要在文档里如实标注，不能用隧道地址冒充满足了容器化要求。

## 十一、已知局限

1. **单机单副本**。`api` 只有 1 个 worker、1 个副本，重启期间服务中断数十秒（要重新预加载）。这是刻意取舍（进程内单例内存约 0.9GB），不是遗漏。
2. **会话态是内存态**。`/api/resume/parse` 返回的 `resume_id` 存在进程内存里，容器重启后失效，用户需要重新粘贴简历。**登录用户"保存的简历"不受影响**（落在 sqlite 数据卷里）。
3. **Agent 结果缓存落盘在卷上**，多副本部署时各副本各有一份缓存，不会共享。
4. **sqlite 不适合高并发写**。当前量级（课程演示）完全够用，真要上量需要换 Postgres。
5. **无 HTTPS**。用 IP 直连演示不需要；若要域名 + HTTPS，前置一层 Caddy 或给 Nginx 加 `listen 443 ssl` 与证书路径即可。
6. **前端产物未做代码分割优化**，`JobView-*.js` 因整包引入 ECharts 高达 1.13MB。这是任务13「优化响应时间」的处理项之一。
7. **镜像约 2GB**，主要是 torch CPU 轮子（BGE 向量模型依赖）。要显著瘦身只能换掉向量模型，而那会改变《大模型应用文档》里已验证的检索口径（P@5 = 0.353），不做。
