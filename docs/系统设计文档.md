## 一、总体架构

```
┌──────────────────────────── 前端（轻）─────────────────────────────┐
│  Streamlit  src/web/app.py                                         │
│  ① 简历输入  ② 匹配推荐  ③ 岗位聚类  ④ 智能问答                     │
│  · 只依赖 requests + streamlit，**不加载任何模型**                  │
└───────────────────────────────┬───────────────────────────────────┘
                                │ HTTP（API_BASE 环境变量）
┌───────────────────────────────▼───────────────────────────────────┐
│  后端  FastAPI  src/api/main.py                                    │
│  /api/health  /api/resume/parse  /api/match  /api/score            │
│  /api/cluster/list  /api/cluster/profile  /api/chat                │
│  服务层 src/api/services.py（进程内单例 + 简历会话态）              │
└───────────────────────────────┬───────────────────────────────────┘
                                │ 进程内函数调用（不重复实现）
┌───────────────────────────────▼───────────────────────────────────┐
│  已有能力层（第 1–2 周成果，全部复用）                              │
│  parse_resume（任务6 简历解析）  match.py（任务6 六维匹配）          │
│  score_features + 4×XGBoost（任务5 评分模型）                       │
│  query.Retriever（任务10 RAG：FAISS + 本地 BGE）                    │
│  agent.Agent + tools（任务10 Function Calling，9 工具）             │
└───────────────────────────────┬───────────────────────────────────┘
                                │
┌───────────────────────────────▼───────────────────────────────────┐
│  数据层（静态文件 + 一个 SQLite）                                   │
│  data/processed/*.csv（8,836 岗位、500 简历、207,640 配对、聚类）   │
│  data/rag/*.npy + jobs_kb_cards.json（8,852 张卡片向量）            │
│  models/*.joblib（4 个上线模型）+ 模型元数据.json                   │
│  data/app.db（SQLite：用户 / 会话 / 简历 / 收藏 / 匹配历史 / 问答） │
└───────────────────────────────────────────────────────────────────┘
```

**两条设计原则**

1. **前端不碰业务**：Streamlit 进程里没有 torch / transformers / faiss / 模型文件，全部经 HTTP 调后端。
   好处：前端镜像可做到 ~150MB、启动秒级；前端可替换成 Vue3 而不动后端一行。
2. **后端不重复实现**：服务层直接复用第 1–2 周的函数（`match_jobs`、`Retriever`、`Agent`），
   保证**接口口径 = 离线脚本口径 = Agent 对话口径**，不会出现"两套数"。

### 2.1 单例与预加载

| 组件 | 加载内容 | 实测耗时 |
|---|---|---|
| 匹配引擎 | 8,836 岗位 + 500 简历 + 技能词典 + TF-IDF 索引 | **2.63 s** |
| RAG 检索 | 8,852×512 向量 + FAISS 内存索引 + 卡片元数据 | **7.51 s** |
| 评分特征构造器 | 岗位侧特征 + TF-IDF 拟合（后台线程预热） | **4.32 s** |
| 岗位/公司浏览库 | 8,836 岗位 + 任务7 簇标签 + **4,096 家公司聚合** | **0.98 s**（首次访问 `/api/jobs` 或 `/api/companies` 时构建） |

- 匹配引擎与 RAG 在 `startup` 事件中**同步预加载**（否则首个请求要等 10 s 才返回）
- 评分特征构造器较重，放**后台线程**预热，不阻塞服务启动
- 三个都做进程内单例，只在首次访问时构建，此后复用

### 2.2 简历会话态（刻意不引入数据库）

```
POST /api/resume/parse  →  返回 resume_id（rs_xxxxxxxxxxxx）
POST /api/match         →  传 resume_id
```

- 存储：**进程内存字典**，TTL **2 小时**，上限 **200 份**，超限按时间淘汰
- **重启即失效**——这是有意的取舍：数据本身是静态文件，引入数据库对课程目标无收益
- 局限如实标注在 `/api/health` 的 `简历会话态.持久化` 字段与本文档 §6

## 三、接口设计（四类 API）

统一约定：
- 所有响应带 `ok`（布尔）；业务错误返回 **400** 且带 `error` + `hint`；参数校验失败返回 **422**（Pydantic）
- **凡涉及数字的响应都带 `来源`**，与项目"每个数字可溯源"一致
- 交互式文档：`http://<host>:8000/docs`（Swagger UI，答辩可直接演示接口契约）

### 3.1 辅助：健康检查

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| GET | `/api/health` | — | `ok`、`启动预加载耗时秒`、`匹配引擎{就绪,岗位数,权重版本}`、`RAG检索{就绪,卡片数,向量维度}`、`评分模型{就绪,特征维度,模型[]}`、`Agent{就绪}`、`简历会话态{在存,TTL小时,上限,持久化}`、`进程运行秒` |

### 3.2 ① 简历输入：解析

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/resume/parse` | multipart：`file`(PDF) 或 表单 `resume_text` | 见下 |
| POST | `/api/resume/parse_text` | JSON：`{resume_text}` | 见下 |

出参：`resume_id`、`来源`（粘贴文本 / PDF(文件名, 页数)）、**`原文`**（解析用的原始正文：粘贴文本原样、PDF 的文本层；前端靠它把简历存成"我的简历"）、`解析字段{姓名,期望岗位,期望城市,最高学历,专业,工作年限,是否应届,期望薪资,...}`、`技能列表[]`、`技能数`、`证书列表[]`、`未在词典的技能[]`、`解析告警[]`

> 两条通路**共用同一个解析器**（PDF 只负责"拿到文本"），因此同一份简历两种输入结果一致
> ——任务6 回归测试：字段命中 **100%（80/80）**、PDF **8/8** 与粘贴文本一致。

### 3.3 ② 人岗匹配

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/match` | `{resume_id \| resume_text, top_n(1~50，默认10)}` | `简历摘要`、`权重版本`、`权重{}`、`推荐数`、`打分范围`、`耗时秒`、`推荐[]`、`来源[]` |

`推荐[]` 每项：`排名`、`总分`、**六维分**（`技能/经验/学历/地域/薪资/专业证书`）、`岗位ID`、`岗位名称`、`公司`、`城市`、`岗位薪资`、`经验要求`、`学历要求`、`技能标签`、`技能命中数`、`岗位技能要求数`、`余弦分`、`距离km`、`推荐理由`

- 对**全量 8,836 个岗位**逐对打分再取 Top-N（实测 **0.29~0.32 s**）
- 技能分 = `0.6 × (0.7×岗位技能覆盖率 + 0.3×简历技能利用率) + 0.4 × TF-IDF余弦×100`
- 权重取 `匹配权重表.csv` 的最新版本（当前 **v2**，在线推荐口径）

### 3.4 ③ 评分（双口径，本版新增）

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/score` | `{job_id(J0001~J8836), resume_id \| resume_text}` | `岗位{}`、**`规则口径{}`**、**`模型口径{}`**、`差异`、`来源[]` |

| 口径 | 内容 | 说明 |
|---|---|---|
| **规则口径（主）** | `总分` + `六维分{}` + `权重版本` + `技能命中数` + `岗位技能要求数` + `TF-IDF余弦` + `距离km` | 任务6 六维加权，可解释，**在线推荐用的就是它** |
| **模型口径（对照）** | `T1回归_预测总分`、`T2分类_匹配概率`、`是否匹配(≥65)`、`特征{}`（36 维）、`模型文件` | **任务5 的 XGBoost 首次有了在线入口**（此前只在离线脚本里跑过） |

> **为什么保留两个口径**：任务8 实测两者 Spearman 秩相关 **0.9909**、Top-10 重合度 **0.788**，
> 说明模型本质是规则的蒸馏。把两个数并排展示，既证明了一致性，也保留了可解释性
> （模型分不带六维明细）。
>
> **口径一致性证据**：`src/api/score_features.py --validate 30` 用离线简历复算 36 维特征，
> 与训练时用的 `匹配特征_全量样本.csv` **逐列完全一致**（实测 10 份简历 × 6,536 个配对 =
> **65,376 个单元格 100% 相同**），保证"线上模型口径 = 离线训练口径"。

### 3.5 ④ 岗位聚类

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| GET | `/api/cluster/list` | — | 主方案（K=9）、簇数、簇[]（簇号/簇名/岗位数/占比/薪资中位数/主导大类/主要城市）、各方案{}、来源[] |

### 3.6 ⑤ 智能问答

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/chat` | `{question(1~500字), use_cache, history:[{role,content}]}` | `回答`、`来源[]`、`工具轨迹[]`、`工具序列`、`轮数`、`耗时秒`、`tokens{}`、`prompt版本`、`模型`、`缓存命中`、**`缓存时间`**、`服务耗时秒` |

- 复用 `agent.Agent.ask()`：DeepSeek Function Calling + **12 个工具**，最多 6 轮 / 12 次工具调用
- 工具轨迹逐步可审计（工具名 + 参数 + 结果摘要 + 来源）
- **`use_cache=false` → 忽略缓存、强制真实调用模型**（前端「🔄 重新回答」走这条）
- **`history` → 带最近几轮对话**（追问"那再列几个"才接得上），最多 6 轮
- **缓存策略（v2.5）**：缓存键 = `Prompt版本|模型|问题`，带 `cached_at`，**TTL 7 天**，过期自动重算；命中时响应带 `缓存时间`，前端显示"缓存（时间）"以示区分
- **依赖外网**：失败返回 502 并提示检查 `.env` 的 `DEEPSEEK_API_KEY`；前端会把**后端真实错误**显示在对话框里（不再用固定兜底句掩盖）

> **前端形态（v2.4 起）**：不再有独立的问答页，改为 **`web/src/components/ChatWidget.vue`**——挂在 `AppLayout` 上的
> **可拖动悬浮球**（右下角默认位、位置持久化到 `localStorage`），单击弹出 **370×520 小对话框**，
> 里面提问、看回答、展开工具轨迹与来源。**接口与后端逻辑完全没动**（这一层只换了交互形态），
> 因此 `/api/chat` 的契约、缓存、工具轨迹、来源列表都可照旧使用与测试。

> **首页（岗位浏览）接口补充**：`GET /api/jobs` 支持 `city` / **`district`（区县）** / `category` / `keyword` / **`source_kw`（精确匹配「来源关键词」列）** / `salary_min` / `edu` / `cluster` / `sort`；`GET /api/jobs/stats` 另返回 **`热门搜索`（来自「来源关键词」列）/ `按城市区县`（区域筛选索引）/ `分类导航`（大类→高频子职位）**，以及「招聘者」相关字段（`招聘者` / `招聘者职位` / `在线状态` / `回复文案` / `同公司岗位数`）——这些字段全部来自真实抓取数据，用于模拟 BOSS直聘 的「招聘者行」与「区域 / 热门职位」筛选。

> **`keyword` 与 `source_kw` 的区别（v2.0 新增，别混用）**：`keyword` 是**模糊**匹配（岗位名 + 公司 + 技能标签 + 职位描述全字段），范围大；
> `source_kw` 是**精确**匹配「来源关键词」列。首页分类卡上写「数据分析 2,564」，点进去必须刚好 2,564 条，所以首页跳转一律用 `?source_kw=`；
> 用 `?keyword=数据分析` 会搜出 2,803 条（多出的是标题/描述里提到该词但不属于该抓取批次的岗位）。`tests/test_home.py` 里有用例专门锁死这两个数字。

> **`分类导航` 的当前用法**：该索引（大类 → 高频子职位，仅保留数量 ≥3 的子职位）**只用于填充首页搜索框的「职位类型」下拉（大类级别）**。
> 首页原先在筛选栏之上另有一块「职位分类导航面板」（左侧大类 + 右侧该大类全部子职位链接），已在 v1.5 按使用者反馈**整块删除**：
> 该面板占屏高较大，而搜索框下拉已覆盖同一筛选能力，删掉后首页动线收紧为「城市 → 搜索 → 筛选 → 职位列表」。
> **后端未改**，`/api/jobs/stats` 仍返回 `分类导航`，保留给后续「点击大类直查」等交互复用。
> **公司视角（按公司名聚合的 `/api/companies` 系列）见 §3.9。**

### 3.7 ⑥ 用户体系：注册 / 登录 / 鉴权

| 方法 | 路径 | 入参 | 出参 / 说明 |
|---|---|---|---|
| POST | `/api/auth/register` | `{username(3~24), password(≥6), role, nickname, phone, email}` | `token` + `expires_at` + `用户{}`（**注册即登录**）；用户名重复/非法角色 → 400 |
| POST | `/api/auth/login` | `{username, password}` | 同上；密码错/用户不存在 → **401**（不区分提示，避免枚举用户名） |
| POST | `/api/auth/logout` | 请求头 `Authorization` | 删除该令牌（**幂等**：不带令牌也返回 200） |
| GET | `/api/auth/me` | 请求头 `Authorization` | 当前用户；无令牌 → 401「未登录」，令牌无效/过期 → 401「登录已失效」 |
| PUT | `/api/user/profile` | `{nickname?, phone?, email?}` | 更新资料（**需登录**） |
| PUT | `/api/user/password` | `{old_password, new_password}` | 校验原密码 → 换新盐重算哈希；原密码错 → 400 |
| GET | `/api/user/stats` | 请求头 | 个人中心概览：简历数/收藏数/匹配次数/提问次数 |

**鉴权实现（可审计）**

| 项 | 做法 |
|---|---|
| 口令存储 | **PBKDF2-HMAC-SHA256，20 万次迭代 + 每用户 16 字节随机盐**，只存 hash 与 salt，**绝不存明文** |
| 口令校验 | `hmac.compare_digest` **常量时间比较**，避免计时侧信道 |
| 会话令牌 | `secrets.token_urlsafe(32)`，落库带过期时间（**默认 7 天**）；登出即删除 |
| 授权方式 | 请求头 `Authorization: Bearer <token>` |
| 越权保护 | 所有个人中心写操作都带 `WHERE user_id=?`，**跨用户改删一律 400**（有专门用例） |
| SQL 安全 | 全部**参数化查询**，无字符串拼接 |
| 角色权限 | `role ∈ {jobseeker, employer, admin}`；`require_role()` 依赖注入，403 时提示所需角色 |

> **注册界面不暴露「角色」选择（v1.9）**：本系统面向求职者，Vue3 与 Streamlit 两套前端的注册表单都已**删除角色选择控件**
> （字段由 4 个减为 3 个：用户名 / 密码 / 昵称），前端不再传 `role`，由后端默认值 `jobseeker` 兜底。
> **后端能力一字未改**：`role` 字段、`employer`/`admin` 角色、`require_role()` 与 403 权限演示全部保留，
> 权限演示所需的非求职者账号通过**接口/测试**创建（`tests/test_auth.py` 仍有 `employer`、`admin` 用例），
> 只是注册页面不再让普通用户自行选择——避免出现"用户给自己选了企业/管理员"的越权入口。

### 3.8 ⑦ 个人中心（求职者）与 ⑧ 权限演示

| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST/PUT/DELETE | `/api/user/resumes`、`/api/user/resumes/{id}` | 简历管理：**一个用户只有一份简历**——`POST` 是**保存或覆盖更新**（已有则覆盖，返回 `简历已保存` / `简历已更新`），`PUT` 改标题/正文，`DELETE` 删除（删掉后可以重新保存一份）；`PUT /{id}/default` 保留兼容（单份恒为默认）。库里由 `init_db()` 保证每人最多一行（启动时会把历史遗留的多份收敛为最近更新的一份） |
| PUT | `/api/user/resumes/{id}/default` | 设为默认简历 |
| GET/POST/DELETE | `/api/user/favorites`、`/api/user/favorites/{job_id}` | 岗位收藏：**只传 job_id，岗位信息由后端查岗位库补齐**（保证与岗位库一致）；重复收藏 400 |
| GET | `/api/user/matches` | 匹配历史（最近 20 次，含 Top-N 摘要与总分）——**接口与入库保留，个人中心已不再展示该列表（v2.4）** |

- `POST /api/match` 支持 `saved_resume_id`（用个人中心保存的简历），并把本次推荐写入**匹配历史**

|---|---|---|---|
| GET | `/api/companies/stats` | — | `总体`（公司总数 4,096 / 在招岗位总数 8,836 / 平均每司 2.16 / 只招 1 个岗位的公司 2,481 / 招 10 个以上 88 / 岗位数最多公司）、`规模分档`、`按城市`（公司数）、`按大类`（公司数）、`热门企业` Top20、`最活跃企业` Top10、`筛选项`、**`口径说明`** |

**公司档案字段全部由该公司在招岗位聚合而来**：在招岗位数、规模分档、城市/区县覆盖、岗位大类分布、
技能需求 Top12、学历/经验分布、薪资上下限中位数与最高值、招聘者列表（姓名/职位/回复文案）、
在线岗位数、今日回复总数、来源关键词、热招职位（前 3 个，排序口径 `今日回复数 → 薪资上限`）。

**两条口径必须如实说明**（接口 `口径说明` 字段仍随 `/api/companies/stats` 返回、`规模分档` 标签有鼠标悬停提示；
v1.7 按使用者反馈**移除了页面左侧的「口径说明」面板**，但口径本身没有放宽，`tests/test_companies.py` 里的"防编造字段"与"分档不重不漏"断言仍在守）：

1. 数据里**没有**「行业 / 规模 / 融资阶段」列，所以接口**不返回**这三个字段，页面也不留位置——不编造；
   「规模分档」用该公司的**在招职位数**代理（`1个 / 2-4个 / 5-9个 / 10-49个 / 50个以上`），不等于员工人数或注册资本。

   故合计大于公司总数 4,096（实测：按城市合计 4,452、按大类合计 5,499），不能当成公司数去加总。

**前端联动**：`web/src/components/CompanyCard.vue`（公司卡，列表与"相似公司"共用）、
`web/src/components/JobDetailDrawer.vue`（**职位详情抽屉，首页/公司页/公司详情页三处共用一个组件**，
v1.6 从 `HomeView.vue` 抽出，避免三份实现走样）。岗位接口的每个岗位同时返回 `公司ID`，
因此**首页岗位卡上的公司名可以直接点进公司详情页**，公司详情页里的岗位又能点开抽屉看完整 JD，形成闭环。

| 方法 | 路径 | 入参 | 出参 / 说明 |
|---|---|---|---|
| GET | `/api/home` | `n`（榜单条数，默认 8，夹在 1~20） | `热门分类`（8 个，含示例岗位/热门技能/平均薪资上限）、`地区推荐`（16 城，含公司数/平均薪资/热门区县）、`高薪岗位`、`热门岗位`、`热门企业`、`热门技能`、`总体`、**`口径说明`**、`来源` |

**榜单口径（全部只用真实列；页面上不展示这些说明，接口与本文档负责讲清）**：

| 区块 | 口径 | 实测（2026-09-18） |
|---|---|---|
| 热门分类（hero 轮播 + 快捷条） | 抓取这批岗位时用的**「来源关键词」列**（真实列，共 8 个），固定榜单 | 数据分析 2564 / 测试 2104 / Java 1317 / Python 956 / 运维 934 / 后端 554 / 算法 271 / 前端 136，合计 **8,836** |

| 高薪岗位推荐 | 候选池 = `薪资下限 > 10000 元/月`（**2,472** 个岗位），**每次请求 `random.sample` 随机抽 8 个**，再按薪资上限降序展示 | 每次进首页都不一样 |
| 热门岗位推荐 | 候选池 = `今日回复数 ≥ 20`（**1,676** 个岗位），**每次请求随机抽 8 个**，再按回复数降序 | 每次进首页都不一样 |
| 热门企业 | 按在招职位数降序 **Top 10**（固定，与公司页同一口径） | 软通动力 86、三一集团 72、外企德科 36… |
| 热门技能 | 全量岗位技能标签计数 Top12（固定） | QE / Python / QC / Java / QA / C++ … |

**随机 vs 固定**：`tests/test_home.py` 同时锁两头——连抽 5 次高薪/热门榜至少出现 2 种组合（证明真的随机），
而地区与热门企业连查两次必须完全一致（证明固定榜单没被打破）；另有用例校验抽出来的岗位确实落在池子里
（`薪资下限 > 10000`、`今日回复数 ≥ 20`）且都能通过 `/api/jobs/{id}` 查到。

**为什么"热门"要写清口径**：数据里**没有**浏览量、投递量、应聘人数这类列，所以不能含糊地说"最热"。
接口把这 5 条口径随响应一起返回（`口径说明`），`tests/test_home.py` 另有"不得出现
`浏览量/投递量/热度/应聘人数` 字段"的诚实性断言。

> **页面展示策略（v2.1 起为硬约定）**：这些口径/来源说明**只在接口与本文档里保留**，
> **页面上不再出现任何"这个推荐/榜单是怎么来的"描述性文字**（按使用者要求）。
> 后续新增或修改前端页面时同样遵守：不写口径、不写数据来源、不写数据规模、不写"如实说明/已知局限"这类说明文字。
> 说清楚口径的责任在接口字段与文档，界面保持干净；数据真实性由 `tests/` 里的断言守着，不靠页面文案。
> `web/scripts/render-check.mjs` 已把这些字样加入"不该出现的内容"反向断言（首页还额外禁 `排序`/`口径`/`随机抽取` 等），
> 一旦回流即报错。

## 六、局限与如实说明

| # | 局限 | 说明 |
|---|---|---|
| 1 | **无人工金标** | 评分/匹配/检索的真值都由规则生成；"模型分"本质是对规则的拟合，**不能宣称准确率** |
| 2 | **简历会话态不持久** | 临时 `resume_id` 存进程内存（TTL 2 小时、重启失效）；但**用户账号、保存的简历、收藏、历史已持久化到 SQLite**（`data/app.db`） |
| 3 | **鉴权仅令牌，无更细粒度** | 无邮箱/短信验证、无密码找回、无登录失败锁定与验证码；令牌 7 天且无刷新机制。生产需补 |
| 4 | **无鉴权保护的接口仍开放** | 匹配/评分/聚类/问答允许**游客**调用（有意设计：便于演示）；个人中心相关接口一律需登录 |
| 5 | **企业侧未实现** | 角色已预留 `employer`，但企业发布岗位、查看候选人等功能未做（按需求"后续补充"） |
| 6 | **对话依赖外网** | Agent 走 DeepSeek API，断网或 Key 失效时 `/api/chat` 不可用（其余接口不受影响） |
| 7 | **双前端**：Vue3（主秀）+ Streamlit（保底） | 两套前端**只走 HTTP、共用同一批接口**，数据口径一致；Vue3 观感好但需要 Node 工具链（开发期 5173，构建产物 `dist/` 由 nginx 托管），Streamlit 依赖最少、部署最简。**Vue3 侧暂无自动化测试套件**，用无头渲染脚本（`npm run check:render`，8 路由）+ 一次性真实点击脚本验证 |
| 8 | **评分模型覆盖** | 模型用任务5 的 500 份离线简历训练；对全新简历的预测属**分布外**，故界面上规则分始终为主口径 |
| 9 | **单进程** | 索引与单例在进程内，多 worker 会各自加载一份（内存翻倍）；SQLite 亦为单文件，当前规模单 worker 足够 |
| 10 | **公司页只有岗位能推出的维度** | 原始数据没有「行业 / 规模 / 融资阶段 / 员工人数」列，公司页因此**不展示**这些（避免编造）；「规模分档」是**在招职位数**的代理口径。公司档案完全由该公司在招岗位聚合，**公司信息与岗位表同源同时效**；按**公司名称字符串精确去重**，所以同一公司的不同写法不会归并——数据里实测有 11 组前缀重合，例如「外企德科」「外企德科数字技术有限公司」「外企德科人力资源服务(福建)有限公司」被算成 3 家（分别 2 / 36 / 1 个岗位），「双环传动」与「双环传动(嘉兴)精密制造有限公司」被算成 2 家（2 / 7 个岗位），另有「…浙江分公司1」这类带数字后缀的脏值；已知 A2 环节的字段错位也会让个别「招聘者」归属不准 |
