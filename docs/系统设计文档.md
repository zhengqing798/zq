## 一、总体架构

```
┌──────────────────────────── 前端（轻）─────────────────────────────┐
│  Streamlit  src/web/app.py                                         │
│  ① 简历输入  ② 匹配推荐  ③ 岗位聚类  ④ 智能问答                     │
│  · 只依赖 requests + streamlit，**不加载任何模型**                  │
└───────────────────────────────┬───────────────────────────────────┘
                                │ HTTP（API_BASE 环境变量）
┌───────────────────────────────▼───────────────────────────────────┐
│  后端  FastAPI  src/api/main.py                                    │
│  /api/health  /api/resume/parse  /api/match  /api/score            │
│  /api/cluster/list  /api/cluster/profile  /api/chat                │
│  服务层 src/api/services.py（进程内单例 + 简历会话态）              │
└───────────────────────────────┬───────────────────────────────────┘
                                │ 进程内函数调用（不重复实现）
┌───────────────────────────────▼───────────────────────────────────┐
│  已有能力层（第 1–2 周成果，全部复用）                              │
│  parse_resume（任务6 简历解析）  match.py（任务6 六维匹配）          │
│  score_features + 4×XGBoost（任务5 评分模型）                       │
│  query.Retriever（任务10 RAG：FAISS + 本地 BGE）                    │
│  agent.Agent + tools（任务10 Function Calling，9 工具）             │
└───────────────────────────────┬───────────────────────────────────┘
                                │
┌───────────────────────────────▼───────────────────────────────────┐
│  数据层（静态文件，无数据库）                                       │
│  data/processed/*.csv（8,836 岗位、500 简历、207,640 配对、聚类）   │
│  data/rag/*.npy + jobs_kb_cards.json（8,852 张卡片向量）            │
│  models/*.joblib（4 个上线模型）+ 模型元数据.json                   │
└───────────────────────────────────────────────────────────────────┘
```

**两条设计原则**

1. **前端不碰业务**：Streamlit 进程里没有 torch / transformers / faiss / 模型文件，全部经 HTTP 调后端。
   好处：前端镜像可做到 ~150MB、启动秒级；前端可替换成 Vue3 而不动后端一行。
2. **后端不重复实现**：服务层直接复用第 1–2 周的函数（`match_jobs`、`Retriever`、`Agent`），
   保证**接口口径 = 离线脚本口径 = Agent 对话口径**，不会出现"两套数"。

## 二、模块设计

| 模块 | 文件 | 职责 |
|---|---|---|
| API 应用 | `src/api/main.py` | 路由、CORS、统一错误格式、**启动预加载** |
| 服务层 | `src/api/services.py` | 单例管理、简历会话态、四类能力的封装 |
| 接口契约 | `src/api/schemas.py` | Pydantic 入参/出参（本文档 §3 的可执行版本） |
| 特征构造 | `src/api/score_features.py` | 单对(简历,岗位) 36 维特征 + 模型推理（**任务5 模型的在线入口**） |
| 前端 | `src/web/app.py` | 四个页签；纯 HTTP 客户端 |
| 一键脚本 | `scripts/run_api.ps1`、`scripts/run_web.ps1` | 启后端 / 启前端 |
| 接口测试 | `tests/test_api.py` + `pytest.ini` | 正常/边界/异常三条路径 |

### 2.1 单例与预加载

| 组件 | 加载内容 | 实测耗时 |
|---|---|---|
| 匹配引擎 | 8,836 岗位 + 500 简历 + 技能词典 + TF-IDF 索引 | **2.63 s** |
| RAG 检索 | 8,852×512 向量 + FAISS 内存索引 + 卡片元数据 | **7.51 s** |
| 评分特征构造器 | 岗位侧特征 + TF-IDF 拟合（后台线程预热） | **4.32 s** |

- 匹配引擎与 RAG 在 `startup` 事件中**同步预加载**（否则首个请求要等 10 s 才返回）
- 评分特征构造器较重，放**后台线程**预热，不阻塞服务启动
- 三个都做进程内单例，只在首次访问时构建，此后复用

### 2.2 简历会话态（刻意不引入数据库）

```
POST /api/resume/parse  →  返回 resume_id（rs_xxxxxxxxxxxx）
POST /api/match         →  传 resume_id
```

- 存储：**进程内存字典**，TTL **2 小时**，上限 **200 份**，超限按时间淘汰
- **重启即失效**——这是有意的取舍：数据本身是静态文件，引入数据库对课程目标无收益
- 局限如实标注在 `/api/health` 的 `简历会话态.持久化` 字段与本文档 §6

## 三、接口设计（四类 API）

统一约定：
- 所有响应带 `ok`（布尔）；业务错误返回 **400** 且带 `error` + `hint`；参数校验失败返回 **422**（Pydantic）
- **凡涉及数字的响应都带 `来源`**，与项目"每个数字可溯源"一致
- 交互式文档：`http://<host>:8000/docs`（Swagger UI，答辩可直接演示接口契约）

### 3.1 辅助：健康检查

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| GET | `/api/health` | — | `ok`、`启动预加载耗时秒`、`匹配引擎{就绪,岗位数,权重版本}`、`RAG检索{就绪,卡片数,向量维度}`、`评分模型{就绪,特征维度,模型[]}`、`Agent{就绪}`、`简历会话态{在存,TTL小时,上限,持久化}`、`进程运行秒` |

### 3.2 ① 简历输入：解析

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/resume/parse` | multipart：`file`(PDF) 或 表单 `resume_text` | 见下 |
| POST | `/api/resume/parse_text` | JSON：`{resume_text}` | 见下 |

出参：`resume_id`、`来源`（粘贴文本 / PDF(文件名, 页数)）、`解析字段{姓名,期望岗位,期望城市,最高学历,专业,工作年限,是否应届,期望薪资,...}`、`技能列表[]`、`技能数`、`证书列表[]`、`未在词典的技能[]`、`解析告警[]`

> 两条通路**共用同一个解析器**（PDF 只负责"拿到文本"），因此同一份简历两种输入结果一致
> ——任务6 回归测试：字段命中 **100%（80/80）**、PDF **8/8** 与粘贴文本一致。

### 3.3 ② 人岗匹配

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/match` | `{resume_id \| resume_text, top_n(1~50，默认10)}` | `简历摘要`、`权重版本`、`权重{}`、`推荐数`、`打分范围`、`耗时秒`、`推荐[]`、`来源[]` |

`推荐[]` 每项：`排名`、`总分`、**六维分**（`技能/经验/学历/地域/薪资/专业证书`）、`岗位ID`、`岗位名称`、`公司`、`城市`、`岗位薪资`、`经验要求`、`学历要求`、`技能标签`、`技能命中数`、`岗位技能要求数`、`余弦分`、`距离km`、`推荐理由`

- 对**全量 8,836 个岗位**逐对打分再取 Top-N（实测 **0.29~0.32 s**）
- 技能分 = `0.6 × (0.7×岗位技能覆盖率 + 0.3×简历技能利用率) + 0.4 × TF-IDF余弦×100`
- 权重取 `匹配权重表.csv` 的最新版本（当前 **v2**，在线推荐口径）

### 3.4 ③ 评分（双口径，本版新增）

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/score` | `{job_id(J0001~J8836), resume_id \| resume_text}` | `岗位{}`、**`规则口径{}`**、**`模型口径{}`**、`差异`、`来源[]` |

| 口径 | 内容 | 说明 |
|---|---|---|
| **规则口径（主）** | `总分` + `六维分{}` + `权重版本` + `技能命中数` + `岗位技能要求数` + `TF-IDF余弦` + `距离km` | 任务6 六维加权，可解释，**在线推荐用的就是它** |
| **模型口径（对照）** | `T1回归_预测总分`、`T2分类_匹配概率`、`是否匹配(≥65)`、`特征{}`（36 维）、`模型文件` | **任务5 的 XGBoost 首次有了在线入口**（此前只在离线脚本里跑过） |

> **为什么保留两个口径**：任务8 实测两者 Spearman 秩相关 **0.9909**、Top-10 重合度 **0.788**，
> 说明模型本质是规则的蒸馏。把两个数并排展示，既证明了一致性，也保留了可解释性
> （模型分不带六维明细）。
>
> **口径一致性证据**：`src/api/score_features.py --validate 30` 用离线简历复算 36 维特征，
> 与训练时用的 `匹配特征_全量样本.csv` **逐列完全一致**（实测 10 份简历 × 6,536 个配对 =
> **65,376 个单元格 100% 相同**），保证"线上模型口径 = 离线训练口径"。

### 3.5 ④ 岗位聚类

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| GET | `/api/cluster/list` | — | 主方案（K=9）、簇数、簇[]（簇号/簇名/岗位数/占比/薪资中位数/主导大类/主要城市）、各方案{}、来源[] |
| GET | `/api/cluster/profile` | `name`（簇名关键词，可空） | 工具的 `summary` + `data[]` + `来源[]`；查不到时 `ok=false`（不报 500） |

主方案 K=9 的定 K 依据：**轮廓系数峰值 0.6735**（肘部法指向 K=5，取轮廓系数并说明取舍）、
**ARI = 1.0000**（换随机种子结果一致）；最大簇占 51.45%，已做二阶细分（K=8）。

### 3.6 ⑤ 智能问答

| 方法 | 路径 | 入参 | 出参 |
|---|---|---|---|
| POST | `/api/chat` | `{question(1~500字), use_cache}` | `回答`、`来源[]`、`工具轨迹[]`、`工具序列`、`轮数`、`耗时秒`、`tokens{}`、`prompt版本`、`模型`、`缓存命中`、`服务耗时秒` |

- 复用 `agent.Agent.ask()`：DeepSeek Function Calling + **9 个工具**，最多 6 轮 / 12 次工具调用
- 工具轨迹逐步可审计（工具名 + 参数 + 结果摘要 + 来源）
- **依赖外网**：失败返回 502 并提示检查 `.env` 的 `DEEPSEEK_API_KEY`

## 四、存储设计

| 数据 | 位置 | 形态 | 是否入库 |
|---|---|---|---|
| 岗位表（8,836×20） | `data/processed/zhaopin_jobs_cleaned_seg.csv` | CSV | ✅ |
| 简历（500×47 / 500×20） | `data/processed/简历数据_{cleaned,seg}.csv` | CSV | ✅ |
| 配对标签（207,640） | `data/processed/匹配样本_标签数据.csv` | CSV | ❌ 可重建（27MB） |
| 配对特征（207,640×36） | `data/processed/匹配特征_全量样本.csv` | CSV | ❌ 可重建（26MB） |
| 数据划分 | `data/processed/匹配样本_划分_按{简历,岗位}.csv` | CSV | ✅ |
| 岗位聚类 | `data/processed/岗位聚类_{标签,簇画像,定K曲线}.csv` | CSV | ✅ |
| 卡片元数据 | `data/rag/jobs_kb_cards.json` | JSON | ❌ 可重建（8MB） |
| 向量矩阵 | `data/rag/jobs_kb_vectors.npy`（8,852×512，L2 归一化） | NumPy | ❌ 可重建（17MB） |
| 上线模型 | `models/*.joblib`（4 个）+ `模型元数据.json` | joblib/JSON | ✅ |
| 会话态 | 进程内存字典 | — | — |

> 无数据库。选型理由：数据是**静态只读**的（一次构建、多次查询），引入 DB 只增加部署复杂度；
> 唯一需要"写"的是简历会话态，用 2 小时 TTL 的内存字典即可，且已如实标注"重启失效"。
> 向量库同样不落索引文件——FAISS 的 C++ 层在 Windows 下无法打开中文路径，
> 改为 `.npy` 落盘 + 启动时内存重建（8,852×512 重建 **<0.1 s**）。

## 五、关键流程时序：上传简历 → 匹配 → 推荐 → 对话

```
用户        Streamlit(8501)           FastAPI(8000)               能力层
 │               │                        │                         │
 │ 粘贴/上传 ───►│ POST /api/resume/parse │                         │
 │               │───────────────────────►│ parse_resume_text/pdf ─►│ 同一解析器
 │               │◄─ resume_id + 字段 ────│                         │
 │               │  (session_state 保存)  │                         │
 │ 点「开始匹配」►│ POST /api/match        │                         │
 │               │─ {resume_id, top_n} ──►│ JobIndex + match_jobs ─►│ 全量 8,836 打分
 │               │◄─ Top-N + 六维分 + 理由 ─│  (0.3s)                │
 │ 看雷达图/理由 ◄│                        │                         │
 │ 点某岗位评分 ─►│ POST /api/score        │                         │
 │               │─ {resume_id, job_id} ─►│ score_pair（规则）─────►│ 任务6
 │               │                        │ PairFeatureBuilder ────►│ 任务5 模型
 │               │◄─ 规则分 + 模型分 + 差异 │  (36 维特征)           │
 │ 点「提问」 ──►│ POST /api/chat         │                         │
 │               │─ {question} ──────────►│ Agent.ask ─────────────►│ DeepSeek 选工具
 │               │                        │  ◄── 工具结果回灌 ──────│ 本地 9 工具
 │               │◄─ 回答 + 来源 + 工具轨迹 │  (缓存命中则秒回)       │
```

**耗时实测**：解析 <0.1s ｜ 匹配 0.29~0.32s ｜ 评分（含模型）0.3~0.6s ｜ 对话 3.4~10.1s（首次）/ 0s（缓存命中）

## 六、局限与如实说明

| # | 局限 | 说明 |
|---|---|---|
| 1 | **无人工金标** | 评分/匹配/检索的真值都由规则生成；"模型分"本质是对规则的拟合，**不能宣称准确率** |
| 2 | **会话态不持久** | 简历会话存内存，TTL 2 小时、重启失效；没有用户体系与历史记录 |
| 3 | **无鉴权** | 课程演示环境，CORS 全放开、无登录；生产需补 API Key / 限流 |
| 4 | **对话依赖外网** | Agent 走 DeepSeek API，断网或 Key 失效时 `/api/chat` 不可用（其余接口不受影响） |
| 5 | **前端为 Streamlit** | 视觉可定制性有限；选它是为了任务12 的容器化与部署复杂度最低 |
| 6 | **评分模型覆盖** | 模型用任务5 的 500 份离线简历训练；对全新简历的预测属**分布外**，故界面上规则分始终为主口径 |
| 7 | **单进程** | 索引与单例在进程内，多 worker 会各自加载一份（内存翻倍）；当前规模单 worker 足够 |
