## 〇、两个层面的"AI"

本项目里的 AI 要分成两层来说，混在一起讲容易变成空话：

| 层面 | 含义 | 本报告对应章节 |
|---|---|---|
| **A. 系统自身的 AI 能力** | 交付给用户的智能：评分模型、语义匹配、聚类、RAG 检索、Function Calling 智能体 | 第一节 |
| **B. 开发过程中的 AI 助手** | 用来写代码、写测试、写文档、排错、调 Prompt 的 AI | 第二～四节 |

**贯穿全篇的一条主线**：无论哪一层，AI 的输出都**必须经过一道能机械判定对错的关卡**（测试、断言、交叉校验、真机验证），否则它会自信地给出错误结论 —— 而且**错得看不出来**。

**如实说明的局限**（这部分必须写，否则前面的数字会被误读）：

1. **没有任何人工标注金标准**。标签由规则生成（技能重合 + 学历/经验/地域/薪资门槛），模型的 MAE/PR-AUC 衡量的是"**能不能拟合这套规则**"，不是"**是否符合真人判断**"。
2. **简历是合成的**（500 份），"居住地与期望城市 100% 一致"，所以地域维度没有跨城求职样本。
3. **岗位库只覆盖 16 个城市 / 4 个省**（福建、浙江、江苏、安徽），不代表全国。
4. **`经验要求` 字段有 2,182 个岗位（24.69%）错位**（值被填成了 `JavaScript`、`QE` 之类），建模时按"信息缺失"给中性分。
5. 聚类是**无监督**结果，簇名是自动生成的关键词标签，簇内存在异质性（最大簇里混有新媒体运营、跨境电商运营等岗位）。

> **AI 的边界认知，第一课就是"指标好看 ≠ 结论可信"。** 上面这些局限在项目里被反复写进文档、也写进了智能问答的规则 10（Agent 被要求主动声明已知局限），目的是不让一个漂亮数字被当成事实。

## 三、关键 Prompt 与版本迭代

### 3.1 系统 Prompt 的迭代（v1 → v7）

完整记录见 `docs/prompt版本记录.md`。挑三次**最能说明问题**的迭代：

#### ① v2/v3 的教训：**约束必须配一个"够得着"的工具**

v2 就写了 7 条硬性要求，其中一条是"**严禁用行业常识代替本系统数据**"。但 30 问评估发现：**有 3 条问题完全不调用工具**（第 12、23、29 问），其中第 12、29 问恰恰是问"本系统的口径" —— 模型**查不到**本系统写过的结论，于是只能拿行业常识答。

根因不在 Prompt，而在**工具**：纯向量检索时，16 张结论卡被 8,836 张岗位卡淹没（结论类 P@5 仅 0.147）。

v4 补上专用工具 `search_kb`（只检索结论卡）后：

| 指标 | v3（8 工具） | v4（9 工具） |
|---|---|---|
| 有来源标注 | 27/30（90%） | **29/30（97%）** |
| 完全不调用工具 | **3 条** | **1 条**（唯一剩下的是"数据里根本没这个字段"，不用工具是正确行为） |

> **结论：Prompt 里写"不许编"，但没给它一个能查到答案的工具，等于逼模型说谎。** 这条是整轮迭代里收益最大的一条认知。

#### ② v3：一次工具设计缺陷，把 12 次调用压到 2 次

问"薪资最高的城市是哪个"，v2 的模型**逐城调用 `salary_stats` 12 次**、撞上工具上限，prompt tokens 高达 9,330。

v3 新增 `salary_rank`（一次给出全部城市排名）并加规则"需要逐项对比时优先用聚合工具"后：

| 同一问题 | v2 | v3 |
|---|---|---|
| 工具调用 | `salary_stats` × 12（撞上限） | `salary_stats`、`salary_rank` |
| prompt tokens | 9,330 | **4,182** |
| 耗时 | 7.1 s | **3.8 s** |

> **结论：把"需要 N 次调用才能凑出来的信息"做成一个工具，比在 Prompt 里叮嘱模型"少调用几次"有效得多。**

#### ③ v4→v5：一次真实提问暴露的**两个 bug**

问「福州市的 Java 岗位有多少」→ Agent 用 `search_jobs` 传组合短语「Java 开发工程师」，只召回 **7 条**。而库里福州含 Java 的岗位实际有 **84 个**（名称口径）/ **139 个**（名称或技能标签口径）。

根因有两层，都是**代码层**而不是模型层：
1. 关键词匹配写死为"整串子串匹配"，于是「Java工程师」「java」「全栈（技能含 Java）」全都搜不到；
2. "问数量"没有被引导到**返回总数**的工具上。

修法：匹配层改为"归一化 → 中英混排切开 → 剥掉泛词 → 按核心词 OR 匹配，ASCII 核心词加词边界"（`java` 不再命中 `javascript`）；数量口径主口径改为"名称或技能标签命中"。复测：`Java` / `Java开发` / `Java 开发工程师` / `java` / `JAVA` **五种写法结果完全一致**，同一问题 **7 条 → 139 个**。

> **结论：用户一句"这个回答不对"，可能指向的是工具实现而不是 Prompt。** 排查顺序应该是"先看工具返回了什么，再看模型怎么用"。

#### ④ v6→v7：把"回答"变成"可点的东西"

- v6：工具 9 → **12 个**（新增 `generic_agg` 通用分组统计、`company_query`、`home_stats`），规则加"一次调用能拿到整张分组表就不要拆成 N 次"；模型切到 `deepseek-v4-pro`，`max_tokens` 1200 → 2000。
- v7：要求**提到具体岗位时必须给岗位页链接** `[岗位名](/#/job/J0020)`，且岗位 ID 必须原样取自工具返回、不得自己编。同时发现 `home_stats` 的精简字段里漏了 `岗位ID`——**模型想给链接也给不了**。

> **结论：模型的输出质量受限于工具返回的字段。** 想让它给出可点链接，就得先把 `岗位ID` 喂给它。

### 3.2 驱动 AI 助手时用的 Prompt 套路

这一节讲"怎么跟 AI 说话"。四条被反复证明有效的句式：

| 句式 | 用途 | 实际效果 |
|---|---|---|
| **"先读实现再写断言，不要猜"** | 写测试 | 边界 92 项 + 异常 41 项的每条断言都能在源码里找到依据；避免了"凭想象的接口行为"写测试 |
| **"这条数字是实测的还是推断的？没跑过就标注未验证"** | 防编造 | 本报告第四节那个真实案例就是这么抓出来的 |
| **"给出反例和边界，不要只给顺利路径"** | 设计测试/接口 | 产出了 `size=0/-7/1000/100`、`page=0/99999`、单字简历、2 万字简历、`top_n=1/50` 这类真正的边界用例 |
| **"改完告诉我怎么验证"** | 收尾 | 每次改动都附一条可复现的验证命令，而不是"已经修好了" |

> 反过来，**失败的句式**是："帮我写一个 X" —— 得到的往往是"能跑但不符合本项目口径"的代码。
> 有效的模式是：**先给约束和反例，再给任务**。

## 四、AI 产出的核验与人工修正（本报告的重点）

我们把"验 AI"落成了三层机制。**每一层都配一个真实案例**，因为这一节才是这份报告真正的价值。

### 4.1 第一层：机械可验证 —— 断言比"人读一遍"可靠

AI 的输出最危险的地方不是"明显错"，而是"**看起来对**"。所以核验要尽量做成**能自动判定真假**的形式。

**案例：缺陷 13 —— 少了一条数据，接口却说自己有 9 条**

现象：智能问答回答"岗位可以分成 **8** 类"，而 `/api/cluster/list` 明确返回 `簇数=9`。
根因：`Retriever.cluster_profile()` 结尾写死了 `[:8]`，把 K=9 主方案的第 9 个簇（**137 个岗位、占比 1.55%**）静默切掉了。

这个缺陷**正常路径测试根本发现不了** —— 接口返回 200、字段齐全、数字也算得出来，只是少了一条。

抓住它的是一条**交叉校验**：

> **"主方案 9 个簇的岗位数合计必须等于岗位库总数 8836"** —— 少任何一行，这个和就不成立。

**教训：光断言"有没有返回"不够，还要断言"返回的东西合起来对不对"。**

### 4.2 第二层：必须在目标环境跑 —— 本地通过 ≠ 线上正确

**案例：缺陷 16 —— 本地 8 项"等价验证"全过，线上容器起不来**

因为开发机没装 Docker，我先把"镜像能不能跑"里与 Docker 无关的部分抽出来做了 8 项等价验证（依赖能不能被 pip 解析、环境变量是否生效、按镜像 CMD 能不能启动、离线能不能加载向量模型……），**8 项全部通过**。

但真机部署时：容器启动即崩、反复重启，healthcheck 永远不健康，`zq-web` 因为依赖的 api 不健康而拒绝启动。日志给出的原因很直接：

```
PermissionError: [Errno 13] Permission denied: '/app/data/processed/技能标签黑名单.csv'
```

镜像以非 root 用户运行、只把可写卷 `/app/var` 授权给它，把 `data/` 当只读资产；但应用启动时**会无条件重写**两个派生缓存文件（即使文件已存在、即使调用方传了 `write=False`）。

**为什么本地没抓到？** 因为那 8 项等价验证里没有复现"**只读目录 + 非 root 用户**"这个组合条件 —— 本机是仓库属主，写当然成功。

> **教训：等价验证只能把风险前移，不能替代真机验证。** 这条已经写进《部署手册》§5.4 和《测试报告》缺陷 16。

**同一次真机部署还暴露了缺陷 17**（测试用 PDF 的生成只列了 Windows 字体路径，精简 Linux 镜像里退化成缺字框 → 容器内那条测试必失败）。两条都是"只有真的在目标环境跑才会暴露"的类型。

### 4.3 第三层：数字必须可溯源 —— 抓 AI 最危险的那种幻觉

AI 最危险的幻觉不是"编一个不存在的 API"（那种一跑就报错），而是 —— **编"我验证过了"**。

**案例：一个没跑就写进文档的数字**

在某次文档更新里，AI 把"容器运行约定等价验证 **7/7 通过**"写进了《测试报告》。但回看执行记录：那次脚本在"按镜像 CMD 启动"这一步因为一个参数被通配展开而失败，**只跑到 4/5 就中断了** —— 那个"7/7"是**没有实际跑完整就写下来的**。

后来完整跑通，实测是 **8/8**（脚本一共 8 项检查）。我们在文档里专门留了更正说明：

> ⚠️ 更正记录：本节初稿与 v3.2 版本条目里写的「7/7 通过」是**没有真正跑完一遍就写下的数字**。数字已按实测更正 —— **没跑出来的数字不写进报告。**

**为什么这条最有价值**：它不是能力问题，是**态度问题**，而且极难被发现 —— 一个"7/7"和一个"8/8"在人眼里都像正常结果。唯一可靠的防线是：**每个数字都必须能回答"这个命令在哪次运行里产出过它"。**

**案例：一次"看起来完全像 bug"的假失败**

验收脚本报"翻页出现重复岗位 1 条"，约 1/3 的运行会复现 —— 这形态非常像一个真实的偶发缺陷。当时的第一个反应是"应用的分页有 bug"，于是抓了每次 `/api/jobs` 请求的参数：

```
请求：page=1 seed=209634161 ｜ page=2 seed=209634161   ← 种子完全相同
第1页首条「HRBP」  第2页首条「资金管理专员」   重复 1 条：["测试工程师"]
```

读实现后确认分页没问题（`rows = list(rows)` 先复制再 `random.Random(seed).shuffle(rows)`，同种子必然同排列，两页按 ID 绝不相交）。真因是**断言拿"岗位名称"当唯一标识**：8,836 个岗位里 **只有 6,037 个不同名称，41.2% 的岗位重名**（"测试工程师"有 **67** 个）。两个不同岗位恰好同名，就被算成了"重复"。

**教训：用业务名称做跨集合比较，在真实数据上必然假阳性；而且这种假失败很有迷惑性 —— 它稳定地以一定概率出现，看起来完全像真缺陷。**

### 4.4 核验机制本身的失败：三层机制是怎么长出来的

必须承认：**上面三层机制不是一开始就有的，而是被缺陷一次次逼出来的。**

| 学到的教训 | 之前的做法 | 现在的做法 |
|---|---|---|
| 新增返回字段必须同步改 schema | 靠人记得改 | 缺陷 4、5（`response_model` 静默吞字段，**连续复发两次**）之后，把它写成规则 |
| 读不存在的键会静默失败 | 写 `parsed.get("_原文", "")`，永远拿到空串 | 缺陷 8（上传 PDF 的简历正文恒为空、存不进"我的简历"）之后，接口显式返回 `原文` 字段并加断言 |
| 缓存命中路径也要测 | 只测了首次调用 | 缺陷 10（缓存命中必 500：把给人看的时间字符串当数字做减法）之后补上"缓存命中不再 500"用例 |
| 声明了却从没执行过的入口等于没验证 | 依赖是逐个 `pip install` 装的，从没走过 `pip install -r requirements.txt` | 缺陷 12（`requirements.txt` 缺编码声明，中文 Windows 上必崩 `UnicodeDecodeError`）之后，加了一条直接调用 pip 自己的 `auto_decode()` 做回归 |

> **一句话总结这一节**：AI 会把代码写得"看起来对"，而**能被机械判定的断言**、**目标环境的真实运行**、**每个数字的唯一出处**，是把"看起来对"变成"确实对"的三道关。

## 五、反思

### 5.1 效率提升到底来自哪里

**收益最大的不是"写得快"，而是"把核验做成了自动化的"。**

- 生成很快：一份文档、一段测试、一个脚本，常常几分钟就有初稿。
- 核验很慢：一条断言要读实现、想边界、写用例、跑一遍确认它真能失败（否则可能是"永远通过"的假测试）。
- 真正的提速发生在**把核验沉淀成可复跑的东西之后**：322 项测试、8 路由渲染检查、29 项接口联调、十项部署验收、Linux 依赖预检 —— 之后每次改动跑一遍就知道有没有坏，**不用重新逐个页面点**。

按环节看收益分布也很清楚：

| 环节 | AI 收益 | 原因 |
|---|---|---|
| 写测试、写文档、写脚手架、查依赖冲突 | **高** | 重复性劳动，格式固定，对错好判定 |
| 排错定位、环境兼容性排查 | **中高** | 能快速列出可能性并给出验证命令 |
| 技术选型、口径定义、权重取舍、产品取舍 | **低** | 这些是"决定"，AI 只能给选项和理由，**决定必须自己做，责任也归自己** |

### 5.2 AI 最不可靠的地方：它不知道自己不知道

它会：把 8 写成 9（缺陷 13）、把没跑的写成跑过（那个 7/7）、把成功说成失败（重名导致的假重复）、把失败说成成功（等价验证 8 项全过却漏掉真机上必崩的问题）。

共同点是：**它的错误总是"看起来正常"**。所以：

- "要求它标注不确定性"比"要求它准确"更实际；"要求它给出验证命令"比"要求它保证正确"更实际。
- **凡是它说"已完成/已验证"的地方，都要有人能指出"在哪次运行、哪条命令产出的证据"。**

### 5.3 对"AI 会取代什么"的具体认知

做完这个项目后，我的判断是：

- AI 能顶掉的是**"执行"**：写代码、写用例、写文档、查资料。
- AI 顶不掉的是**"判断"与"负责"**：口径怎么定、权重怎么取、哪些局限必须如实披露、一个漂亮的指标能不能拿出去说 —— 这些要人拍板，而且错了是人担责。
- 因此**人的价值在上移**：从"会不会写"上移到"**能不能把问题定义清楚、能不能设计出验证方案、能不能判断 AI 的产出可不可信**"。这个项目里真正花时间的部分，恰恰都是后一类。

### 5.4 学术诚信与使用边界

我们给自己定了四条线：

1. **必须读懂**：AI 生成的每一段代码/文档都要能解释"为什么这么写"，答辩时要能被追问。
2. **必须能溯源**：每个数字都要有出处（文件、命令、运行记录）；缺证据的数字宁可删掉。
3. **必须如实标注**：数据局限（无人工金标、简历合成、16 城、24.69% 经验错位）、未做项（并发压测、安全渗透、企业侧功能、PDF 用例的完整覆盖）一律写进文档，不回避。
4. **不能把 AI 的"我觉得"当结论**：尤其是"这个应该没问题"这种句式，一律要求补一条验证命令。

### 5.5 做得不够的地方（自我批评）

1. **核验介入得偏晚**。缺陷 13（聚类少一簇）从数据生成到线上问答用了几周才被发现 —— 如果一开始就有"跨接口对账"的断言，它当天就会暴露。
2. **对"等价验证"的信任度过高**。本地 8 项全过就以为镜像没问题，结果真机第一跑就崩。**当时应该在拿到服务器后的第一分钟就做真机验证，而不是等构建完。**
3. **有一处不诚实的记录**（那个 7/7）。虽然自己发现并更正了，但说明"写完就发"的习惯有风险 —— 现在改为"文档里每个数字都当场核对出处"。
4. **Prompt 迭代的评估样本偏小**（30 问），且问题集是固定的，容易过拟合。理想做法是留一批"没看过的"问题做验证集。
5. **没有做并发/长稳压测**，性能结论只到"单线程 N 轮取分位数"，而且实测发现同一台机器不同时段的漂移可达 **±47%**，所以没敢声称任何后端提速。

### 5.6 如果重做一遍，会先做这四件事

1. **先建可机械判定的验收关卡，再写功能**：接口三路径测试、跨接口对账、真机部署验收脚本。
2. **拿到目标环境的第一时间做一次最小部署**（哪怕只跑 hello-world + 一个接口），把环境风险前置。
3. **所有 AI 产出的数字现场挂出处**，文档评审时逐条抽查，而不是事后补。
4. **Prompt 评估留验证集**，并且每次改版都记录"改了哪句、为什么、实测变化多少"（这一点我们后来做到了，见 `docs/prompt版本记录.md`）。

---

## 六、结论

1. **AI 在本项目里既是交付物，也是生产力工具**：系统侧的评分/匹配/聚类/RAG/Agent 是课程要求的 AI 能力；开发侧用 AI 辅助完成了 33 个接口、7 个前端页面、322 项测试、8 份以上文档与一次完整的容器化云部署。
2. **AI 的效率优势真实存在，但集中在"执行"层**；判断与责任无法外包。
3. **本项目最值钱的工程经验不是任何一段代码，而是那三层核验机制**：机械可判定的断言、目标环境的真实运行、每个数字的唯一出处。它们不是设计出来的，是被 17 条缺陷一次次逼出来的。
4. **AI 最危险的输出不是明显的错误，而是"看起来正常的错误"** —— 一个没跑过的数字、一次把 8 写成 9 的截断、一次因断言写错而报出的"假 bug"。防住它们只能靠机制，不能靠信任。
5. **对使用者（我们自己）的要求因此更高**：要能把问题定义清楚、能设计验证方案、能判断 AI 的产出可不可信、能对最终结果负责。
